## 1. 技術スタック

| 項目 | 内容 |
| --- | --- |
| フレームワーク | Next.js 16.3.3 App Router / React 19 / Turbopack |
| 言語 | TypeScript |
| DB | PostgreSQL（本番 Neon / ローカルも Neon 可）、Prisma 6.19.3 |
| 認証 | Google OAuth 2.0（`googleapis`）。ログイン＝Google 連携を兼ねる |
| 通知 | Web Push（`web-push` / VAPID）＋ Service Worker (`public/sw.js`) |
| AI | OpenAI（既定 `gpt-4o-mini`、`OPENAI_MODEL` で変更可）。未設定時はルールベースにフォールバック |
| スタイル | Tailwind v4（`@import "tailwindcss"` / `@theme inline`）。白黒トークン設計 |
| デプロイ | Vercel（`prisma generate && next build`）。cron は外部から `/api/cron/poll` を叩く |

- Prisma Client の出力先は `generated/prisma`（`schema.prisma` の `generator.output`）。
  `binaryTargets = ["native", "rhel-openssl-3.0.x"]`。
- マイグレーションはローカルで実行: `./node_modules/.bin/prisma migrate deploy` → `prisma generate`。
  `datasource` は `DATABASE_URL`（pooled）と `DIRECT_URL`（直結・マイグレーション用）。

### Tailwind v4 の注意
- important 修飾子は**サフィックス**（`text-surface!`）。プレフィックス（`!text-surface`）は無効。
- 要素の既定スタイル（`a{}`, `h1,h2,h3{}`）は必ず `@layer base` に置く。unlayered だと
  `@layer utilities` に勝ってしまい `text-white` などが効かなくなる（CTA 文字消えバグの原因）。
- テーマトークンは `app/globals.css`。`--teal*` / `--accent*` は無彩色化済み。
  `--warn` / `--warn-soft` は赤（失敗警告の例外）。`--chart-amount` / `--chart-count` はグラフ専用。
  `--scope-event*`（青）/ `--scope-genre*`（緑）/ `--scope-keyword*`（紫）は「次回の出し方」チップ専用
  （`app/components/scope-chip.tsx` だけで使う。白黒基調の例外として §12 に記載）。

## 3. データモデル（`prisma/schema.prisma`）

### 3.1 認証・ユーザー
- **User** `{ id, name?, email(unique), createdAt, tutorialSeenAt? }` — 本人識別は `email`。
  ログイン毎に upsert。`tutorialSeenAt` は導入チュートリアルの完了/スキップ時刻
  （PWA で `localStorage` が分かれても再表示しないためサーバー側にも保持）。
- **UserGoogleAccount** `{ userId(unique), googleAccountEmail, accessToken, refreshToken?,
  tokenExpiry?, calendarId="primary", lastSyncedAt?, syncToken?, watchChannelId?, watchResourceId?,
  watchExpiration?, writeDescriptionEnabled=true }` — トークン管理と watch チャンネル、
  説明欄書き込みのオプトイン（既定 true）。
- **PushSubscription** `{ userId, endpoint(unique), p256dh, auth, userAgent? }` — 1 ユーザー複数端末。

### 3.2 予定・準備リスト
- **Category** `{ userId, name, @@unique([userId,name]) }`
- **Event**（要フィールド）
  - `title, eventDatetime, endDatetime?, memo?, googleEventId?, recurringEventId?`
  - `@@unique([userId, googleEventId])` — **ユーザーごとに一意**（全ユーザー共通の一意制約に
    していた時期があったが廃止。招待・共有された予定は複数ユーザーのカレンダーに同じ
    googleEventId で現れることがあり、全ユーザー共通だと後から連携した側の取り込みが
    一意制約違反で黙って失敗していた＝自分の予定が一切取り込まれない不具合になる）。
  - `source "google"|"manual"`, `categoryId?`
  - `autoManaged`（既定 true）— 自動生成・説明欄書き込みの対象か。連携時に既にあった予定は false。
    アプリで能動的に触ると true になる（`markAutoManaged`）。
  - `listCustomized` — 個別編集して同名グループから切り離したか。
  - `listCleared` — 意図的に全消しした状態。true の間は自動生成・提案なし（「何も出さない」を学習）。
  - `sectionOrder` — 枠キーと表示順の JSON `string[]`。既定 `["task","belonging"]`。
    センチネル `"@futuremsg"`（`FUTURE_MESSAGE_KEY`）が「💌 未来の自分へ」枠の位置を持つ
    （旧センチネル `"@faillog"` は `lib/sections.ts` の `parseSectionOrder` が読み込み時に除去する）。
  - `listReviewedAt?` — 生成物を編集せず「確認しました」を押した日時。**編集でも `markAutoManaged`
    経由でセットされる**（＝編集＝確認済み扱い）。null かつ EditRecord 無しで「未確認」。
  - `failureWarningAckAt?` / `noFailureAt?` / `postFailureCheckNotifiedAt?` — 失敗ログ機能
    （全廃済み。§6 参照）が使っていた列。UI・コードからの参照は無いが、後方互換のため
    列自体は残置してある（本番昇格時に段階移行できるように）。
  - `futureMessageCheckedAt?` — 「未来の自分へのメッセージ」の AI 判定（genre_ai/similar_ai）を
    この予定に対して一度試したか（結果の有無に関わらず）。予定ごとに1回だけに抑えるための
    キャッシュ。キーワード／ジャンル関連語／カテゴリ一致（安価な判定）はこれと無関係に毎回試す。
  - `messageReviewNotifiedAt?` — 予定後の「メッセージを更新しませんか？」通知の送信日時
    （旧 `postFailureCheckNotifiedAt` に相当。1予定1回の送信管理）。
  - `notifiedAt?` — 新規追加通知を送った日時。
  - `lastWrittenHash?` — 最後に説明欄へ書いた内容のハッシュ（再書き込み・ループ防止）。
  - `lastInboundHash?` — 直近取り込んだ受信テキストのハッシュ（webhook と cron の二重取り込み防止）。
  - リマインド系: `listReminderLeads`（JSON `number[]`・分・最大5・早い順、`[]`=送らない）、
    `sentListReminderLeads`（送信済み JSON `number[]`、leads 変更で `[]` にリセット）、
    `listReminderLeadMinutes?`（先頭値ミラー・後方互換）、`listReminderTouchedAt?`（明示変更で学習停止）。
- **ChecklistItem** `{ eventId, kind, title, comment?, isDone, isUserAdded, sortOrder,
  notifyLeadMinutes?, notifiedAt?, isSuggested, suggestionType?, suggestionRuleId?,
  suggestionValue?, sourceTemplateId? }`
  - `kind` = `"task"`（準備すること）/ `"belonging"`（持ち物）/ ユーザー枠名。
  - `comment` はユーザーの自由メモ（学習対象外だが説明欄には出る）。
  - `isSuggested=true` は confidence 低めの提案行（UI では現在ほぼ非表示）。
  - `sourceTemplateId?` — 名前付きリスト（`ListTemplate`）由来なら元テンプレートの id。
    `saveChecklist` の保存で毎回作り直されるが、タイトルの追加/削除が無い間だけ引き継ぐ
    （§7.2）。`onDelete: SetNull`（テンプレート削除で null に戻るだけ、項目自体は残る）。
- **ChecklistItemImage** `{ eventId, kind, slot(=正規化タイトル), data(data URL), width, height, bytes }`
  - `saveChecklist` は項目行を毎回作り直すため、画像は項目 id ではなく `(eventId, kind, slot)` で紐づく。

### 3.3 学習（spec 9.2）
- **EventFeature** `{ eventId(unique), isOverseas?, durationNights?, isWeekday, timeBucket?,
  keywords, eventLengthBucket? }`
  — 予定の軽い特徴量（ルールベース推定）。`eventLengthBucket`（`"short"|"half_day"|"full_day"`、
  `endDatetime - eventDatetime` から算出、終了時刻なしなら `null`）は保存のみで
  `featureSignature` には含めない（後述、カテゴリ横断パターンでだけ使う）。
- **EditRecord** `{ eventId, categoryId?, addedItems, removedItems, timingChanges, notifyChanges }`
  — 個々の編集の生ログ（JSON）。
- **LearnedRule** `{ categoryId, featureSignature, itemKind, ruleType, target, value?,
  confidence, confirmedCount, contradictedCount, lastConfirmedAt, isUserLocked,
  slotType?, patternTemplate?, aiConfidence?,
  @@unique([categoryId,itemKind,ruleType,target,featureSignature]),
  @@index([ruleType,slotType]) }`
  - `ruleType` = `"exclude_item"` | `"fixed_item"` | `"timing_override"` | `"notify_override"` |
    `"pattern_item"`（カテゴリ横断パターン、下記 §7.1）。
  - `featureSignature` = `{d?,o?,w?,t?}` の JSON（`lib/signature.ts`）。`"{}"` は何にでも当たる。
  - `confidence` は反復確認で上昇、矛盾で低下、未更新で経年劣化。`CONFIDENCE_THRESHOLD = 0.7`。
    `pattern_item` はこの式を使わず、`confirmedCount`/`contradictedCount` の差だけで強さを見る（§7.1）。
  - `slotType`/`patternTemplate`/`aiConfidence` は `pattern_item` 専用（他の `ruleType` では未使用）。

### 3.4 未来の自分へのメッセージ（§6 参照）
- **FutureMessage** `{ userId, body, keywords(JSON string[]), genres(JSON string[]),
  genreKeywords(JSON {genre,terms[]}[]), categoryIds(JSON string[]), scope, archivedAt?,
  contextSummary?, sourceEventTitle?, sourceCategoryId?, confirmedCount, lastConfirmedAt? }`
  - `scope`: `"keyword"`（既定・キーワード一致のみ）/ `"similar"`（似た予定で提案）/
    `"once"`（今回だけ。確定時に `archivedAt` をセット）。
  - `keywords`/`genres`/`categoryIds` は既存 schema の他モデル（`EventFeature.keywords` 等）に
    合わせて JSON 文字列で持つ（`lib/future-messages.ts` の `parseStrArray`/`stringifyStrArray`）。
  - `genreKeywords` はジャンル保存時に一度だけ AI 展開した関連語（`expandGenreKeywords`）。
    ユーザーが編集すれば次回の展開でその分は保持される。
  - **2026-10-10〜**: `genres`/`categoryIds`/`scope`（3択）は画面からは編集できなくなった
    （§12.5 参照）。新規作成・編集後のメッセージは常に `genres:[]`、`categoryIds:[]`、
    `scope:"keyword"` で保存される。一致判定（`cheapMatch`）自体は後方互換でそのまま
    対応しているので、既存データのジャンル一致・`"similar"`/`"once"` も引き続き働く。
- **EventFutureMessage** `{ eventId, messageId, userId, status, matchedBy, matchReason?,
  notifiedAt?, reviewNotifiedAt?, @@unique([eventId,messageId]) }` — 予定×メッセージの
  結びつき（一致判定の結果）。
  - `status`: `"shown"`（提示中）/ `"removed"`（この予定からだけ外した）/
    `"confirmed"`（予定後に確定）/ `"skipped"`（今回は更新しない）。
  - `matchedBy`: `"keyword" | "genre_keyword" | "category" | "genre_ai" | "similar_ai" | "manual"`。
  - 一度 `"removed"` にした組は、同じ条件のままでは再結びつけしない（`upsertLink` が
    既存行の有無だけを見る。ユーザーが明示的に外した判断を尊重するため）。
- **MessageProposalRecord** `{ userId, messageId, eventId, proposed(JSON), final(JSON),
  fieldChanged(JSON {body,keywords,genres,categoryIds,scope:boolean}), acceptedAsIs }`
  — 予定後の確定カードで「提案した内容」と「最終的にユーザーが確定した内容」の記録。
  次回以降の提案（初期選択・修正されにくい根拠文）を**そのユーザー自身の過去の修正**から
  改善するための学習データ（§6.4）。全クエリ `userId` 必須、他ユーザーのデータは一切参照しない。
- 上記3テーブルはすべて **`userId` を持ち、全クエリで `userId` を条件に含める**設計
  （`scripts/test-user-isolation.mjs` で監査）。

> 旧・失敗ログ機能の **FailureLog** / **SavingsEntry** / **FailureDismissal** は全廃済みだが、
> テーブル・列自体は削除せず未使用のまま残してある（本番昇格時に段階移行できるように。
> コード・UI からの参照はすべて外してある）。

### 3.5 テンプレート・その他
- **ListTemplate** `{ userId, kind, name, sourceEventId?, @@unique([userId,kind,name]) }` /
  **ListTemplateItem** `{ templateId, kind, title, notifyLeadMinutes?, sortOrder }`。
  `kind` は「その予定でどの枠に入るか」（`task`/`belonging`/ユーザーが決めた新しい枠名。
  `lib/sections.ts` の枠キーと同じ体系）。`name` はテンプレート自体の名前（一覧・検索用）で
  `kind` とは独立。`kind` を `task`/`belonging` 以外にして作ると（`NewTemplateForm` の
  「その他（新しい枠）」）、適用したとき **その名前の枠が別枠として独立する**（§7 参照）。
- **Feedback** `{ userId, wtpYen?, comment?, screen? }` — WTP アンケート。/admin で閲覧。
- **ActivityMinute** `{ userId, minuteAt(UTC・分丸め), dayKey(JST "YYYY-MM-DD"),
  @@unique([userId,minuteAt]) }` — /admin の利用時間集計専用。詳細は §11。

  - `DeleteLearnedEventButton` は葉の `<summary>` ではなく、`leaf-body.tsx` の「編集」ボタンの
    横（`<details>` の本文側・展開後にだけ見える通常の flex 行）に置く。`<summary>` の外なので
    preventDefault/stopPropagation は不要だが、同じコンポーネントを使い回すため付いたままでも
    害はない。
  - カテゴリ削除 = `deleteCategory(categoryId)`。`Category` を削除するだけ
    （`Event` の categoryId は `onDelete: SetNull`、`LearnedRule` は
    `onDelete: Cascade` で一緒に消える。`FutureMessage.categoryIds` は JSON 文字列の
    ID 参照でリレーションが無いため、削除後もその ID が残る＝マッチ対象にならなくなる
    だけで実害は無い）。
  - 学習された予定の削除 = `forgetLearnedEvent(eventIds)`（`leaf.eventId` と
    `leaf.siblingEventIds` をまとめて渡す）。**ChecklistItem は消さない。**
    `EditRecord` を削除し `listCustomized/listReviewedAt/listCleared` をリセットするだけ
    ＝ `getLearningNameTree` の抽出条件（EditRecord あり／listCustomized／listReviewedAt／
    listCleared のいずれか）に当たらなくなり、次回描画でツリーから消える。実データの
    予定・準備リストの中身はそのまま残る（「学習済みの印」を外すだけ）。
（失敗ログ機能の全廃に伴い、旧 `failure-review-row.tsx` / `sticky-review-rows.tsx` は
削除済み。「未来の自分へ」の一覧編集は `app/failures/message-list.tsx` の `EditableRow` が
同様の役割を担うが、状態管理はよりシンプル：一覧自体は毎回サーバーから取得し直す前提で、
楽観更新の「行が消えない」スナップショット機構は持たない。）

## 6. 未来の自分へのメッセージの内部仕様（`lib/future-messages.ts` ＋ `lib/message-proposal.ts`）

「いつ入るか分からない予定」のために先に書いておくメッセージを、キーワード／ジャンル／
カテゴリの一致で自動的に結びつけ、予定後の確定カードで次回への引き継ぎ内容へ育てていく機能。
旧・失敗ログ機能（再発防止の警告・節約ダッシュボード）を全廃した後継。

> **2026-10-10 以降の注意**: ジャンル・カテゴリでの一致判定（§6.1 の genre_keyword / category /
> genre_ai）は、画面からは新規に設定できなくなった（§12.5）。新規・編集後のメッセージは
> `genres`/`categoryIds` が常に空になるため、実質 keyword と similar_ai（AI 類似判定）だけが
> 効く。以前からジャンル・カテゴリが設定済みの既存メッセージには、引き続きこの節のとおり働く
> （一致判定のコード自体は変えていない。後方互換）。

### 6.1 一致判定 — `ensureFutureMessageMatchesForEvent(eventId, {allowAi, notify})`
判定の対象テキストは `予定タイトル + stripSonaeBlock(memo)`（自アプリのブロックを除く＝
自己一致防止）。`normalizeMatchText`（NFKC・小文字化・カタカナ→ひらがな）で正規化して比較する。
安価な順に試す:
1. **keyword** — `FutureMessage.keywords` のいずれかが対象テキストに部分一致。
2. **genre_keyword** — `genreKeywords`（ジャンルごとの AI 展開済み関連語）のいずれかが一致。
3. **category** — 予定の `categoryId` が `FutureMessage.categoryIds` に含まれる。
4. **genre_ai** / **similar_ai** — 上記で当たらず、かつ `opts.allowAi` かつ
   `Event.futureMessageCheckedAt` が未設定のときだけ、候補を絞って（`genres.length > 0` または
   `scope==="similar"` のものだけ）1回の AI 呼び出し（`aiJudgeMessages`）で判定する。
   結果の有無に関わらず `futureMessageCheckedAt` をセットし、同じ予定で AI 判定を
   繰り返し呼ばない（安価な判定は無関係に毎回試す）。
- 過去（終了済み）の予定・120日より先の予定には新規に結びつけない。
- 一度 `EventFutureMessage.status="removed"` にした組は、同じ条件のままでは再結びつけしない
  （`upsertLink` は既存行の有無だけを見る）。
- 新しく結びついた分は `notifyNewLinks` で即座にプッシュ通知する（`opts.notify !== false` の
  とき。`matchedBy` に応じて文面を変える）。
- **判定のタイミング**: `lib/sync.ts` の `syncAndNotify`（取り込み・更新時。新規予定ぶんだけ、
  AI 判定は1回の同期で最大5件の予算）／予定詳細を開いたとき（`checklist-section.tsx`、
  `allowAi:true`）／メッセージの条件編集時（`updateFutureMessage` →
  `rematchMessageAgainstUpcomingEvents`、今後の予定にだけ新たに一致させる。既存の
  結びつきは条件を変えても外さない＝ユーザーの目の前で行が消える体験を避ける方針）。

### 6.2 ジャンルの関連語展開 — `expandGenreKeywords`
`FutureMessage` の作成・更新時、`genres` に新しい値があれば `expandOneGenre`（OpenAI）で
関連語（6〜12個程度）を展開し `genreKeywords` に保存する。既存のジャンルは再展開しない
（ユーザーが関連語を編集していれば保持）。OpenAI 未設定時はジャンル語（末尾の「系/関連」を
除いた形）をそのまま1語だけ関連語にする。
**画面からジャンルを送らなくなった（§12.5）ため、2026-10-10 以降はこの経路をほぼ通らない**
（`genres` が常に空配列で来るので `expandGenreKeywords` は何もしない）。関数自体は
`item-scope.ts` の `buildRuleData`（`genre` スコープ・後方互換のみ）とも共有している。

### 6.3 予定後の確定カード — `buildMessageProposal` / `confirmMessageReview`
`getPendingMessageReviewsForEvent` / `getPendingMessageReviews`（`status="shown"` かつ
予定終了済み）の各メッセージについて、`buildMessageProposal` が本文追記案・キーワード・
ジャンル・カテゴリ指定・`scope` の全項目をあらかじめ埋めた提案を1回の AI 呼び出しで作る
（OpenAI 未設定時は「変更なし」を返す）。**画面（`message-review-card.tsx`）には本文・
`ScopeQuickToggle`・キーワードの文章欄しか出していないため、提案のうちジャンル・カテゴリは
捨てている**（AI 呼び出し自体は未整理のまま残っている。§12.6）。ユーザーは直すところだけ直して
`confirmMessageReviewAction` を呼ぶと:
- `FutureMessage` を `final` の内容で更新し `confirmedCount` を増やす（`scope==="once"` なら
  `archivedAt` もセット）。
- `EventFutureMessage.status` を `"confirmed"` にする。
- `recordProposalOutcome` が `proposed`/`final` の差分を `MessageProposalRecord` に記録する
  （`fieldChanged` = 項目ごとに変更があったか、`acceptedAsIs` = 全項目そのまま確定したか）。

「今回は更新しない」は `skipMessageReviewAction` → `status="skipped"`（`scope` は変えない）。

### 6.4 学習（ユーザー自身の修正傾向） — `lib/message-proposal.ts`
`buildMessageProposal` はそのユーザーの直近5件の `MessageProposalRecord` から
「項目ごとにそのまま確定した割合」（`acceptanceRateByField`）を計算し、割合が低い
（＝よく修正されている）項目があれば、その旨をプロンプトへの判断材料として渡す
（強制的な指示にはしない。「迷ったら変更しない」を基本方針として、修正されがちな項目は
より慎重に、という程度の調整）。**他ユーザーの `MessageProposalRecord` は一切参照しない**
（`userId` スコープのクエリのみ）。

### 6.5 `/failures` の分類（`app/failures/page.tsx`）
- 確定待ち（`getPendingMessageReviews`、最大 `MAX_REVIEW_PROPOSALS=10` 件ぶん AI 提案を作る）
  を `<MessageReviewCard>` として上部に並べる。
- 「メッセージを書く」フォーム（`createFutureMessageAction`）は予定に紐づけなくても作れる
  （あとで一致すれば自動で結びつく）。🎤 音声入力は `message-dictation-input.tsx` →
  `previewDictatedMessages`/`saveDictatedMessages`（整える→確認→保存の2段階。**いきなり
  保存しない**。失敗ログ機能で確立した恒久ルールをそのまま踏襲）。
- 「これまでの記録」（`message-list.tsx`）は3つの折りたたみ:
  - 「▸ 登録したメッセージを見る」＝ `archivedAt` なし（`EditableRow` で `ScopeQuickToggle`
    （常時表示・即切り替え）＋ 開くと本文・`KeywordSentenceField` を自動保存編集、「過去に移す」「削除」）。
  - 「▸ これからの予定に出るメッセージを見る」＝ 上記のうち `upcomingEvents.length > 0`
    （`listFutureMessages` が `status="shown"` かつ未来のリンクをまとめて返す）。
  - 「▸ 過去のメッセージを見る」＝ `archivedAt` あり（「復活する」で `archived:false` に戻す）。
- **ナビのドット（`layout.tsx`）は `pendingMessageReviewWhere(uid)`（`lib/future-messages.ts`）で
  `prisma.eventFutureMessage.count` する。** 確定待ちの表示条件と必ず同じ意味に保つこと。

### 6.6 事後通知 — `notifyPendingMessageReviews(userId)`（cron から）
- 対象: `messageReviewNotifiedAt == null` かつ終了済み（過去48時間以内）かつ
  `EventFutureMessage.status="shown"` が1件以上残っている予定。
- 通知は**予定単位**で1回（同じ予定に複数のメッセージが pending でも1通）。繰り返し系列は
  系列ごとに1回まで。文面は「『予定名』のメッセージを更新しませんか？」、遷移先は
  `/failures#review`。

### 6.7 主な 未来の自分へ 関連 Server Action（`app/actions.ts`）
- `createFutureMessageAction` — `/failures` の「メッセージを書く」フォーム。`body` のみ必須。
- `createMessageForEventAction` — 予定詳細の「＋ 追加」。新規メッセージを作り、その予定にも
  `matchedBy:"manual"` で結びつける。
- `updateFutureMessageAction` — 本文・キーワード・`scope` の編集（自動保存）。フォームは
  `genres`/`categoryIds` も受け取れる互換性は残しているが、2026-10-10 以降の画面は常に
  空で送る。キーワード/`scope` を変えたら `rematchMessageAgainstUpcomingEvents` で
  今後の予定にだけ再一致させる。
- `archiveFutureMessageAction` / `deleteFutureMessageAction` — 過去に移す⇄復活 / 完全削除。
- `removeMessageFromEventAction` — その予定からだけ外す（`status="removed"`）。
- `previewDictatedMessages(text)` / `saveDictatedMessages({eventId, items})` — 音声入力の
  整える→確認→保存の2段階（§6.5）。
- `confirmMessageReviewAction` / `skipMessageReviewAction` — 確定カードの確定・スキップ（§6.3）。

### 6.8 いつでも編集できる場所（予定詳細・学習内容）
- **予定詳細**（`checklist-section.tsx` → `future-message-editor.tsx` → `FutureMessageRows`）:
  この予定に結びついたメッセージを、`status` が `shown` / `confirmed` / `skipped` のものすべて
  出す（`getMessagesForEvent`）。確定カードは `pending`（shown かつ終了済み）のときだけ上に出るが、
  行の編集は確定後も常に可能。
- **学習内容**（`/savings` → `lib/learning.ts` の `getLearningNameTree`）: 各予定の葉に
  `futureMessageLinks`（同じ3 status）を `messages` として積む。同じ名前でまとめた葉は、
  まとめた予定ぶんのメッセージを連結して出す（各行は自分の `eventId` を持つので、
  「この予定から外す」は元の予定に対して働く）。葉の下に「💌 未来の自分へ」枠として
  `FutureMessageRows`（同じ部品）を出す。
  - 注意: 樹形図に出るのは**学習対象の予定だけ**（準備リストがあり、確認・編集済み、または
    空にした予定）。メッセージだけあって学習対象でない予定は、学習内容には出ない。
- **済んだ予定からの振り返り**: 行の `eventEnded`（`isEventEnded`: 終了日時、無ければ開始日時を
  過ぎているか）が true の行には「📝 振り返り」ボタンを出す（`ReopenableReview`＝
  `app/components/message-review-reopen.tsx`）。押したときだけ `loadMessageProposalAction(linkId)`
  で AI 提案（`buildMessageProposal`）を取り、`MessageReviewCard` を `allowSkip={false}` で開く
  （「今回は更新しない」は出さない）。閉じると提案は捨てる。確定は既存の `confirmMessageReviewAction`
  （本文・キーワード・根拠つき。`final.scope` は常に `"keyword"` を渡す）。
  予定が進行中（未終了）の行は、従来どおり行の編集欄だけ（振り返りボタンは出ない）。
- どちらも保存は `updateFutureMessageAction`（自動保存・`categoryIds` は `getAll` で受け取る）。
  `id` は `FutureMessage.id`、`eventId` は行の持ち主の予定。

## 7. 準備リスト生成・学習フロー

1. **生成**: 予定詳細を開いたとき（`autoManaged=true` のみ自動、`false` ならボタン経由）・
   新規予定の先行生成（`primeNotifiedChecklists`）・「作り直す」（`regenerateChecklist`）などから
   `ensureChecklistForEvent` → `buildChecklistForEvent`
   （`recallBaseChecklist` で似た過去予定から再現、無ければ `generateBaseChecklist` で OpenAI 生成）
   → `getApplicableRules` の LearnedRule を適用（fixed/exclude/timing）。
   `generateAndSaveChecklist` はこれとは別に、`recalled.customSectionSeeds`（似た過去予定で
   名前付きリストがそのまま使われていた枠）があれば `addSeedItemsToEvent` で追加する
   （§7.2）。
   - **2026-10〜、`allowAiGeneration`（既定 true）**: 再利用できる過去予定が無いとき、
     AI でベースを新規生成するかどうか。**カレンダー連携による自動生成だけ `false`**
     （`primeNotifiedChecklists`・予定詳細を開いたときの遅延生成＝`checklist-section.tsx`
     の `needsGeneration && event.autoManaged` 分岐）。`false` のときは、学習元
     （再利用・確定 `LearnedRule`・範囲ルール＝`ChecklistScopeRule`・カテゴリ横断パターン）
     が一つも当たらなければ何も生成しない（空のまま。ユーザー指定: 「学習元があるなら
     それだけ頼り、無ければ自動生成しない」）。「🪄 準備リストを作る」「作り直す」のような
     **手動操作では `allowAiGeneration` は既定の `true` のまま**で、学習元が無くても従来どおり
     AI でたたき台を作る。`buildChecklistForEvent(eventId, { allowAiGeneration })` →
     `generateAndSaveChecklist(eventId, { allowAiGeneration })` →
     `ensureChecklistForEvent(eventId, { allowAiGeneration })` と素通しする。
2. **編集の保存**: `saveChecklist`（Server Action）が該当 `kind` の非提案項目を入れ替え。
   - 追加/削除/タイミング変更があれば `recordEdit`（EditRecord 作成＋LearnedRule upsert：追加→`fixed_item`
     confirm＆矛盾する `exclude_item` を contradict、削除→`exclude_item` confirm＆`fixed_item` を contradict）。
   - `markAutoManaged`（`autoManaged=true` ＋ `listReviewedAt` セット）。
   - 内容が変わった編集なら `resolveNameGroupOnEdit` で同名グループの波及/切り離しを更新。
   - `after()` で `syncEventDescription`（本人＋同名 twin）。
   - 非提案項目が 0 になったら `listCleared=true`（＋残った提案も削除）。
3. **並べ替え**: `sectionOrder`（JSON `string[]`）を ▲▼ で更新。`"@futuremsg"` は「💌 未来の自分へ」枠の位置。
4. **学習の粒度**: LearnedRule は `categoryId × itemKind × ruleType × target × featureSignature`。
   confidence は反復確認で上昇・矛盾で低下・経年劣化。「精度を上げる」ためのもので、リストを増やす方向には使わない。

### 7.2 名前付きリスト（テンプレート）は「別の枠」として独立する

`task`/`belonging` は AI が再生成できる組み込みの2枠。ユーザーが「その他（新しい枠）」で
作った名前付きリスト（`ListTemplate.kind` が task/belonging 以外）は、それとは別の、
その枠名がそのまま見出しになる独立した枠として扱う（説明欄の `【見出し】` も同じ、
`lib/description.ts` の `buildSonaeBlock` が `sectionLabel(key)` で見出しを組み立てる
ため、枠キーさえ正しければ追加のコードは不要）。

- **手動で「適用」**（`applyTemplateToEvent`）: 元のテンプレートの `kind`（task/belonging を
  含む）に関わらず、常に**テンプレート名そのもの**を枠キーにして追加する（ユーザー指示）。
  「準備すること」の枠から「📋 マニュアルから追加」を押しても、そこには混ざらず
  テンプレート名の新しい枠ができる。以前は `it.kind === "belonging" ? "belonging" : "task"`
  で強制的に組み込み2枠へ潰しており、名前付きリストの枠が独立しない不具合もあった。
  `copyListFromEvent`（他の予定からコピー）は対象がテンプレートではなく一過性の過去予定
  なので対象外＝コピー元の `kind` をそのまま使う。
- **共通処理 `addSeedItemsToEvent`**（`lib/checklist.ts`）: テンプレート適用・他の予定からの
  コピー・下記の自動再利用が共通で使う。同じ枠・同じ名前はスキップ、まだ無い枠キーは
  `event.sectionOrder` にも追加する（＝独立した枠として表示される）。`revalidatePath` は
  呼ばない（Server Action からも `generateAndSaveChecklist`（RSC 描画中に呼ばれる）からも
  安全に呼べるようにするため。Server Action 側は呼び出し後に自分で `revalidateAppViews` する）。
- **似た過去予定からの自動再利用**（`recallBaseChecklist` の `customSectionSeeds`、ユーザー指示）:
  似た過去予定（`recallBaseChecklist` の通常のタイトル類似度判定と同じ）の、ユーザーが
  足した枠の中身が、保存済みの名前付きリストと**完全一致**（正規化したタイトルの集合が
  同じ）していたら「そのまま使われていた」とみなし、`generateAndSaveChecklist` が
  `addSeedItemsToEvent` で今回の予定にも同じ枠として追加する。1文字でも違えば
  （＝その場限りの手打ちだった可能性があるため）引き継がない、安全側の判定。
  `task`/`belonging` の再生成とは別トランザクションで、AI 生成 (`buildChecklistForEvent`) の
  結果には含まれない（`BuildChecklistResult.customSectionSeeds` として分離して返す）。
  **`generateAndSaveChecklist` は `opts.force`（「作り直す」）のときはこれを適用しない**
  （ユーザー指示）。「作り直す」は組み込みの2枠だけを作り直す操作という既存の前提
  （このファイル冒頭のコメント「ユーザーが足した枠は AI では再生成できないので残す」）を
  この自動再利用でも守るため。守らないと、ユーザーがこの予定でその枠を消す／編集した
  あとに（無関係のつもりで）「作り直す」を押しただけで、消したはずの枠が勝手に
  復活してしまう。適用されるのは実質、その予定のチェックリストが本当に1件も無い
  状態から初めて生成するとき（`count === 0` かつ `force` 無し）だけ。
  `findVerbatimTemplateSeeds` はテンプレートを `kind` と `name` の両方で探す
  （`applyTemplateToEvent` 適用後の枠キーはテンプレート名そのものになるため。
  `kind` 側の一致も残しているのは、コピー等で `kind` のまま付いた古いデータとの互換用）。
- **予定詳細から「引き出す」（適用）はユーザーが足した枠でも使える**: 以前は
  `checklist-section.tsx` が `templates`/`pastEvents` を `builtin ? … : []` で組み込みの
  2枠にしか渡しておらず、ユーザーが足した枠（例: 旅行セット）の「📋 マニュアルから追加」
  モーダルには何も表示されなかった。`templates={tplByKind(key)}` に変更し、枠キーが
  一致する名前付きリストならどの枠からでも選べるようにした（`pastEvents`＝他の予定から
  コピー、は `getEventsWithLists` が task/belonging の件数しか持たないため、現状は
  組み込み2枠のみに留めている。将来ユーザー枠にも対応するなら `PastEventWithList` を
  枠ごとの件数を持つ形に拡張する必要がある）。
- **`ChecklistItem.sourceTemplateId`**（マイグレーション `20260917090000_checklist_source_template`）:
  この項目が名前付きリストの適用・上記の自動再利用で追加されたものなら、その元
  `ListTemplate.id`。`saveChecklist` は保存のたびに非提案項目を全部作り直すが（他の
  suggestionType 等と同様）、そのとき `sourceTemplateId` を引き継ぐのは「タイトルの
  追加/削除が無かった（＝まだテンプレートのまま）」ときだけ。他の予定からのコピー
  （`copyListFromEvent`）もコピー元の `sourceTemplateId` を引き継ぐ（＝コピーしただけ
  なら「そのまま使っている」ため）。
- **中身を編集したら「◯◯（編集済み）」に改名する**（`saveChecklist`、ユーザー指示）:
  `sourceTemplateId` が付いた枠（＝ task/belonging 以外）で、保存時にタイトルの集合が
  実際に変わった（追加または削除。メモ・チェック・通知タイミングだけの変更では変えない。
  `added`/`removed` は学習用の既存ロジックで isUserAdded な行を毎回含んでしまうため、
  ここでは `nextTitles` と `prevByTitle` の集合だけで厳密に判定する）ときだけ、その予定
  だけ枠名を `${元テンプレート名}（編集済み）` に変える（`effectiveKind`）。sectionOrder
  の置き換え、`ChecklistItem.kind`/`ChecklistItemImage.kind` の付け替えまで同じ保存の
  トランザクションで行う。改名後に作り直す行は `sourceTemplateId` を持たないので、次回
  以降の保存では条件が成立せず、二重に「（編集済み）」が付くことはない。改名先の枠名が
  既にこの予定の別枠として存在する場合はそちらへ合流する（`renameSectionKind` と同じ
  考え方）。組み込みの2枠（task/belonging）は対象外。
- **予定詳細で「⭐ 名前をつけて保存」した枠も、テンプレート名に改名する**
  （`saveListAsTemplate`、ユーザー指示）: 以前は保存する枠を `readKind()` で
  task/belonging に強制しており、ユーザーが足した枠から保存すると項目の絞り込みまで
  壊れていた（`(it.kind === "belonging" ? "belonging" : "task") === kind` が
  task 系の枠を全部まとめて拾ってしまう）。いま編集中の枠キーをそのまま使うよう修正し、
  保存後は `renameSectionKind`（`lib/checklist.ts` の共通ヘルパー。`addSeedItemsToEvent`
  とは別に、既存項目の枠を丸ごと付け替える用）でこの予定の枠自体をテンプレート名に
  改名する（枠名とテンプレート名が既に同じ、または組み込みの2枠からの保存なら改名しない）。
  改名の有無にかかわらず、以後の編集検知のため項目に `sourceTemplateId` を付ける。

### 7.1 カテゴリ横断パターン提案（`ruleType="pattern_item"`）

同じカテゴリ内でしか効かない §7 の学習とは別に、「新幹線の時間を確認する」のような項目を
一般化しておき、**別カテゴリの予定**でも「◯◯の時間を確認する」の形で転用できるようにする仕組み。
既存の学習（confidence 計算式・`featureSignature` の一致条件）には一切触れず、完全に独立に動く。

1. **学習（`recordEdit` の追加項目ループ内）**: ユーザーが項目を追加保存するたびに
   `classifyItemPattern`（OpenAI）で「固有名詞をスロットに置き換えても意味が通る、短く定型的な
   内容か」を判定する。true なら `slotType`（例:「交通手段」）と `patternTemplate`
   （例:「{slot}の時間を確認する」）を添えて `createPatternRuleIfNew` で
   `LearnedRule(ruleType="pattern_item")` を作る（`confirmedCount=contradictedCount=0` で開始）。
2. **適用（`suggest.ts` の `buildPatternItems`）**: 予定の準備リストを組み立てる最後に、
   `getKnownPatternSlotTypes` でユーザーが1件でも学習済みの `slotType` を確認 → あれば
   `matchEventToSlotType` で今回の予定のタイトル・キーワードがどれかの `slotType` に
   当てはまるか判定（辞書一致 → ダメなら AI）→ 当てはまれば `getApplicablePatternRules` で
   その `slotType` のルールを取得し、`confirmedCount - contradictedCount >= 2` または
   `aiConfidence >= 0.8` の「強い」ものだけを `patternTemplate` の `{slot}` を埋めて追加する。
   `isSuggested:false`・`suggestionType:"pattern_analogy"` で、見た目は通常の確定項目と同じ
   （提案の UI は出さない＝目立たない中間状態を作らない方針）。同じ内容の項目が既にあれば
   重複させない。似た過去予定をそのまま再現した回（`recalled`/`verbatim`）には足さない。
3. **フィードバック（`saveChecklist`）**: `saveChecklist` は保存のたびにその `kind` の非提案項目を
   全部作り直すが、`suggestionType` は次回以降に引き継がない。そのため
   「`pattern_analogy` が付いたまま迎える保存」は必ず1回だけ発生し、そこで
   ユーザーがその項目を残したか消したかを見て `LearnedRule.confirmedCount`/`contradictedCount`
   を1増やす。以後の再保存ではもうタグが外れているので二重にカウントされない。
   却下（`contradictedCount > confirmedCount`）に転じたパターンは以後どのカテゴリにも出さない。

**実装時に元の依頼（PDF）から変更した点:**
- 依頼では予定自体の長さを `featureSignature` の新しいキーに含める案だったが、
  `featureSignature` の `d` は既に宿泊数由来のバケット（`durationBucket`）で使用済みのキーであり、
  ここに新しい意味を足すと既存の同一カテゴリ学習（exclude/fixed/timing_override）の
  枝分かれ方まで変わってしまう。既存の学習挙動は変えない方針のため、`eventLengthBucket` は
  `EventFeature` に保存だけして `featureSignature` には含めていない
  （`pattern_item` はカテゴリを跨ぐので、そもそも `featureSignature` 一致では検索せず
  `slotType` だけで横断検索する設計にした）。
- 依頼では「思い出し（recall）は `recurringEventId` で判定している」前提だったが、
  実際の `lib/recall.ts` はタイトル類似度＋カテゴリで判定しており `recurringEventId` は見ていない。
  そこで「前回とほぼ同じ内容をそのまま出す回には仮提案を足さない」という依頼の意図は、
  既存の `recalled`/`verbatim` フラグ（`buildChecklistForEvent` 内で recall が効いたかどうか）を
  そのままスキップ条件として使うことで実現した。

## 8. Google カレンダー連携フロー

1. **OAuth**: `/api/auth/google`（既定は `GOOGLE_SCOPES_WITH_WRITE`＝`calendar.events` 込み。`?write=0` で読み取りのみ）
   → `/api/auth/google/callback` で `User` upsert、`UserGoogleAccount` 保存、初回 `syncAndNotify`。
2. **差分同期**: `syncAndNotify` が `events.list` を `syncToken` で差分取得 → `Event` upsert →
   `classifyEventCategoriesBatch` でカテゴリ推定 → 新規予定を push（初回同期は送らない）→
   予算内で準備リスト先行生成。
3. **push 通知（webhook）**: `ensureWatch` で `events.watch` チャンネルを期限前に張り直す。
   `/api/google/webhook` が変更を受けて同期＋`applyInboundDescription`。
4. **保険のポーリング**: 外部 cron が `/api/cron/poll`（`x-cron-secret` 認証）を叩き、全ユーザーを差分同期、
   watch 更新、`notifyPendingMessageReviews`、`sendDueItemNotifications` / `sendDueListReminders`。
5. **アプリ→カレンダー書き込み**: `syncEventDescription` が `writeDescriptionEnabled` かつ Google 由来かつ
   `autoManaged` の予定について、元メモ＋自ブロックを合成して書く。`lastWrittenHash` と一致ならスキップ（ループ防止）。
   「未確認」（`listReviewedAt` 無し＆EditRecord 無し＆`listCustomized` 無し）のリストは「※まだ確認されていません」
   の注記付き、または書き込み自体を保留。
6. **カレンダー→アプリ取り込み**: `applyInboundDescription` が説明欄の自ブロックをパースし ChecklistItem に反映。
   `lastInboundHash` で webhook と cron の二重取り込みを防ぐ。構造変化のみ学習＆正規化して書き戻し。
7. **連携切れの可視化**（`UserGoogleAccount.syncError` / `syncErrorAt`、追加のみのマイグレーション
   `20261008000000_google_sync_error`）: Google 側でリフレッシュトークンが失効・取り消しされると
   （`invalid_grant`）、`events.list` がエラーになる。以前はこれがどの経路でも黙って失敗し
   （`pullCalendarChanges` は catch して握りつぶす、手動の「カレンダーから取り込む」ボタンは
   uncaught で画面がエラーになる）、新しい予定が入らなくなっても原因が分からなかった。
   - `lib/google.ts` の `isReauthRequiredError(err)` で判定し、`lib/sync.ts` の `syncUserCalendar` が
     `events.list` 失敗時に `syncError: "reauth_required"` を保存してから rethrow、
     成功時は（`lastSyncedAt` 更新と同じタイミングで）`null` に戻す。
   - `/settings` が `account.syncError` を見て警告文＋いつからかを表示（既存の「再接続」ボタンで直せる）。
   - `syncCalendar()`（手動ボタン）は try/catch して失敗時も画面を壊さない（設定画面の表示で気づく形にする）。
   - 再接続（`/api/auth/google/callback`）のトークン保存時に `syncError` を `null` に戻す。
   - **原因そのもの**（リフレッシュトークンの失効）はコードでは直せない。本人が `/settings` の
     「再接続」から Google に再認可するしかない。Google Cloud Console の OAuth 同意画面が
     「テスト」公開ステータスのままだと、リフレッシュトークンは発行から概ね7日で失効する
     （これが繰り返し起きるなら、同意画面を「本番」に進めることを検討）。

### 8.1 カテゴリの自動生成（`lib/categories.ts` + `lib/sync.ts`）
- カテゴリは固定の一覧ではなく、必要になった時点でいつでも自動的に増える。
  `getOrCreateCategory(userId, name)` が `@@unique([userId, name])` への upsert で、
  無ければ作る／あれば既存を返す（呼び出し側は存在チェック不要）。
- **判定の優先順位**（`resolveCategoryForEvent`）: ① `inferCategoryName` のキーワード規則
  （既定5カテゴリのどれかか「その他」を高速に返す。新しい名前は作らない）→ ②キーワードで
  決まらず `useAi=true` なら OpenAI（`classifyEventCategory`）が**既存カテゴリから選ぶか、
  無ければ新しい名前を作る**→ ③どちらも駄目なら「その他」。
- **同期経路ごとに AI 判定のタイミングが違う**（速さとコストのトレードオフ）:
  - 連携直後の初回取り込み（`syncUserCalendar(..., { skipAiCategory: true })`）・webhook の
    即時取り込みはキーワードのみ（AI 呼び出し無し・高速）。
  - cron のポーリング（`syncAndNotify` 経由、`skipAiCategory` 未指定）は取り込み時に
    `resolveCategoryForEvent` を `useAi=true` で呼ぶ（`aiBudget` で1回の実行あたり上限あり）。
  - webhook は取り込み直後に `refineFallbackCategories(userId)` を呼び、直近15分に
    `autoManaged=true` で入って「その他」止まりの予定だけを事後に AI で振り直す
    （同名の既存予定のカテゴリを流用できればそちらを優先し AI 呼び出しを省く）。
  - 連携直後の初回取り込み分（`autoManaged=false`）は上の webhook 経路の対象外
    （`autoManaged` 条件が合わない）なので、`app/api/auth/google/callback/route.ts` が
    `after()` で `refineFallbackCategories(user.id, 20, { firstSync: true })` を別途呼ぶ
    （時間の縛りを外し `autoManaged=false` を対象にする分岐。レスポンス＝ログイン後の
    リダイレクトはブロックしない）。
- **手動での新規作成**: `app/events/category-select.tsx`（`<CategorySelect>`、予定一覧・予定詳細で共用）
  の一番下に「＋ 新しいカテゴリを作る」を常設。選ぶと `window.prompt` で名前を聞き、
  `updateEventCategory` Server Action へ渡す。このアクションも内部で `getOrCreateCategory` を
  使うため、既存の名前と衝突しなければそのまま新規カテゴリになる。select は `value` を state で
  持つ制御コンポーネントにしてあり、prompt をキャンセル/空欄で送ったときは選択を元の値へ戻す。

## 9. 通知（Web Push）

- **購読**: `NotifyEnableButton` / `PushControls` が `Notification.requestPermission()` →
  `reg.pushManager.subscribe({ applicationServerKey: VAPID })` → `savePushSubscription`。
- **送信**: `sendPushToUser(userId, {title, body, url?, tag?})` が全 `PushSubscription` に送信。
  404/410 は購読を削除。`payload` は JSON 文字列で `url`/`tag` を含む。
- **タグ**: `event-<id>` / `prep-<id>` / `listreminder-<id>` / `futuremsg-<eventId>`
  （一致時のお知らせ）/ `msgreview-<eventId>`（予定後の確定うながし）/
  `series-<recurringId>` / `test`。すべて送信側で `url` を明示している。`urlFromTag()` は
  `url` が欠けたとき用の保険で、送信側のタグ命名と対応させる（`futuremsg-`→`#message-review`、
  `msgreview-`→`/failures#review`、`event-|prep-|listreminder-`→`/events/<id>`、
  `series-`→`/events`、未知→`null`→呼び出し側で `/`）。
- **SW（`public/sw.js` v13）**:
  - `push`: `data.json()` → `showNotification(title, { data:{ url } , tag, renotify })`。
  - `notificationclick`: `data.url || urlFromTag(tag) || "/"` を解決 →
    0) `rememberPendingNav(targetHref)` で行き先を IndexedDB（`sonae-nav` db の `kv` ストア、
       key `"pending"`、値 `{url, at}`）に控える（他の手段がすべて効かなくても、アプリが
       次に見えるようになったときに拾えるようにする保険。詳細は下記）。
    1) ハッシュまで同 URL の窓があればフォーカスだけ
    2) 既存の同一オリジン窓を**新規窓を増やさず**目的ページへ。フォーカス中／可視の窓を
       先に、`client.navigate(targetHref)` が通る窓が見つかるまで**全窓を順に試す**
       （同じパスでハッシュ違いだけなら `postMessage({type:"navigate"})`）
    3) どの窓も動かせなければ、フォーカス中の窓へ `postMessage` しつつ **`openWindow` も必ず実行**
       （「通知を開いても何も起きない」を防ぐ最終保険）
  - 既存タブに居るまま `#message-review` などハッシュだけ変わるケースは `ScrollToHash` が
    `hashchange` でも走るので拾える。
  - SW を編集したら先頭コメントのバージョン番号を必ず上げること（`skipWaiting` + `clients.claim` で更新。
    このコメントの `v13` はその時点の値なので、実ファイルの値を都度確認する）。
- **通知タップの行き先を IndexedDB にも控える保険**（`sw.js` の `rememberPendingNav` /
  `sw-register.tsx` の `consumePendingNav`、ユーザー指定）: 上記 `postMessage`/`navigate()` は
  「タップした瞬間、対象の窓の JS が動いている」ことが前提。インストール済み PWA（特に iOS）は
  バックグラウンドの窓が一時停止していて、通知タップでフォアグラウンドに戻ってもすぐには
  メッセージを処理できないことがあり、これが「通知を押してもそのページに飛ばない」の
  有力な原因と考えられる（実機の挙動は環境依存で、こちらの開発環境では web push の
  実機検証はできないため、確度の高い一般的な PWA の既知の制約への対策として実装）。
  `sw.js` は `notificationclick` のたびに行き先を IndexedDB に書き、`sw-register.tsx` は
  マウント時＋`visibilitychange`（`visible` になった瞬間）のたびに読んで消費する
  （読んだら削除＝1回きり。60秒より古い、または既に現在地と同じ URL なら何もしない）。
  他の手段が先に成功していても、この層は「既に正しいページにいる」を検知して自然に
  何もしないので、二重にナビゲートすることはない。

## 10. その他の運用ルール・落とし穴

- **編集＝確認済み**: ユーザー編集アクションは `markAutoManaged` を通し、`listReviewedAt` もセットする。
  「確認しました」ボタンは“見たが何も変えていない”ケース用に残す。
- **自動保存でスクロールを飛ばさない**: `revalidateAppViews()` は `revalidatePath("/", "layout")` の
  総なめ。その画面に**route-level の `loading.tsx`（＝セグメント Suspense 境界）があると、
  自動保存の再検証でフォールバックが再表示されてスクロールがトップに戻る**。`/savings` の
  `loading.tsx` はこの理由で削除した。重い集計ページでも `loading.tsx` は置かない
  （初回遷移は前の画面を保持したまま待つ。全面スケルトンは元々出していない）。
  新しく重いページを足すときも同様に注意する。
- **読み込み中のスケルトンにアニメーションを付けない**（ユーザー指定・恒久ルール）。
  `ChecklistSectionSkeleton`（`checklist-section.tsx`）・`PageSkeleton`（`skeleton.tsx`）は
  元は Tailwind の `animate-pulse` で明滅させていたが、「予定詳細を開くとき点滅してぴかぴか
  する」と不評だったため外し、静止したプレースホルダーにした。新しく骨組み表示を足すときも
  `animate-pulse` 等の明滅・点滅系アニメーションは使わない。
- **自動保存の徹底**: 更新/保存ボタンは置かない。テキストはデバウンス、select は即時、
  保存中は `<AutosaveIndicator>`（右下・黒地・キーボード回避）。
  ただし「変更がないのに autosave/再生成を走らせない」こと。
- **デバウンス中に画面を離れても保存する**（ユーザー指定・恒久ルール）: `setTimeout` で
  デバウンスする自動保存は、React のクリーンアップが `clearTimeout` するだけだと、
  編集直後に画面を離れる／アプリがバックグラウンドになる／閉じると、保存が一度も
  走らずに変更が消えていた。`app/components/use-flush-on-hide.ts` の `useFlushOnHide(flush)`
  を、デバウンスのタイマーに渡すのと同じ `flush` 関数（「保留中の変更があれば今すぐ
  保存、無ければ何もしない」）で呼ぶと、`visibilitychange`（hidden）・`pagehide`・
  アンマウント（画面遷移含む）のどれでも即座に保存を試みる。現在
  `checklist-editor.tsx`・`template-editor.tsx` で使用（`future-message-editor.tsx` の
  行編集は `onBlur` ベースの即時保存のため使っていない）。新しくデバウンス自動保存を
  足すときも、デバウンスの発火関数を独立させて `useFlushOnHide` に渡すこと。
  （実際にページが破棄される瞬間に発火したリクエストは、ブラウザ側の制約で
  完了前に打ち切られることがある＝100%の保証ではないが、何もしないより大幅に安全）。
- **削除は必ず確認**: `window.confirm` か `ConfirmButton`。行が消える/移動する操作も対象。
  フィードバック（WTP アンケート）の送信も対象（`FeedbackWidget` は `ConfirmButton`、
  `/settings` の方は `SubmitButton` の `confirm` prop）。
- **新規ボタンは「似た処理のボタンの横」に置き、縦幅を増やさない**（ユーザー指定・恒久ルール）。
  新しい操作を足すときは、まずその画面・その枠の中にある「一番似た処理をするボタン」を探し、
  同じ flex コンテナに `gap` で並べて追加する。新しい行・新しい `<div>` として上や下に
  積み増さない。実例: 「未来の自分へ」の「🎤 話して記録する」は、`/failures` では
  「作成する」の隣に置く（予定詳細の「＋ 追加」の隣には置かない＝本文欄自体がスマホの
  マイクキーでの音声入力に対応しているため重複）。
- **確定カードは離脱・確定まで消えない**: `MessageReviewCard` は確定/スキップを押すと
  その場で完了メッセージの表示に切り替わるだけで、一覧から即座に消えたりページ内で
  再配置されたりはしない（ページを離れる・再訪するまでは同じ位置に残る）。
- **サーバーが振り直す id をクライアントの key にしない**: `saveChecklist` は項目行を毎回
  作り直す（＝ id が保存のたびに変わる）ので、`initialItems` から作る `key`（`ChecklistEditor`）
  も自動保存のたびに新しくなる。この `key` を Set などの状態のキーにして「保存を跨いで」
  参照すると、保存が完了した瞬間に一致しなくなって状態が消える／リセットされる
  （実例: 行の詳細欄の開閉。§5 の `checklist-editor.tsx` 参照）。保存を跨いで残したい
  クライアント状態は、id ではなく正規化タイトルなど**保存で変わらない値**をキーにすること。
- **JST 固定**: 日時の表示・入力は日本時間（`lib/format.ts` の `parseJstDate` 等）。
- **ビルド**: `prisma generate && next build`。型チェックが OOM することがあるので、必要なら
  `NODE_OPTIONS=--max-old-space-size=6144 npm run build`。
- **Prisma のファイルシステム動的アクセス警告**（`generated/prisma/*` の 2 件）は既知・無害。
- Windows のパス表記の罠: 正しくは `カレンダーwithマニュアル`（`カレンダーwにマニュアル` は誤り）。

## 11. 管理画面・アナリティクス（`app/admin/page.tsx`）

> ⚠️ **この章（11章）は非公開情報を含む。一般ユーザー向けには絶対に公開・共有しないこと**
> （このドキュメント自体も、Artifact 等で外部に出す・見せるときはこの章を除く／伏せる）。
> 管理者メールアドレス・管理者の追加手順は運営者だけが知っていればよい情報であり、
> 公開すると誰でも `ADMIN_EMAIL` を推測して悪用しようとする動機を与えてしまう。

運営者（`ADMIN_EMAIL` に一致する email）だけが開ける。一般ユーザーには 404。
個々のメッセージ・準備リストの**本文は表示しない**（件数などの集計のみ）方針。

### 11.0 運営者（管理者）の追加・削除の仕方
- 管理者かどうかは、環境変数 **`ADMIN_EMAIL`** に載っている Google メールアドレスと
  ログイン中の email が一致するかどうかだけで決まる（`lib/admin-auth.ts` の `isAdminEmail()`。
  `app/admin/page.tsx` から使う）。DB にロール等のフィールドは無い。
- **複数人を管理者にするには、カンマ区切りで並べる**: `.env` では `ADMIN_EMAIL="a@example.com,b@example.com"`
  のように引用符で書く（シェル変数の慣習）が、**Vercel の環境変数の入力欄には引用符を含めない**
  （`a@example.com,b@example.com` とそのまま入力する。`"..."` を含めて貼ってしまうと、
  値の一部に引用符の文字がそのまま入り、`isAdminEmail()` の比較が一致しなくなる）。
  前後の空白・引用符は `isAdminEmail()` 側でも一応取り除くが、想定外の貼り付けミスを
  100% 防げるとは限らないので、設定時は引用符を含めていないか目視でも確認すること。
  前後の空白は無視し、大文字/小文字も区別しない。
- 追加・削除の手順:
  1. ローカル: `.env` の `ADMIN_EMAIL` を編集（`.env.example` にもプレースホルダあり）。
  2. 本番（Vercel）: プロジェクトの **Settings → Environment Variables** で `ADMIN_EMAIL` を
     編集 → 再デプロイ（環境変数の変更は再デプロイしないと反映されない）。
     **ここに管理者以外のメールアドレスが紛れ込んでいないか、変更のたびに必ず見直すこと**
     （検証用に一時的に追加した別アドレスの消し忘れなどが、実質的な権限漏れの原因になる）。
  3. `ADMIN_EMAIL` に追加した本人は、次に `/admin` を開いたときの Google 再ログイン
     （11.0.1 参照）でそのまま認識される。特別な再連携作業は不要。
  4. `ADMIN_EMAIL` を空にする／該当アドレスを外すと `/admin` は再び全員 404 になる
     （テストユーザーとしての Google 側の許可とは無関係の、別の権限）。
- **管理者アカウント自体を新規に用意する場合**は、まず普通にそのメールアドレスで
  一度ログインしてアプリの `User` レコードを作ってから（あるいは先に `ADMIN_EMAIL` に
  追加しておいてから初回ログインしても良い）、`ADMIN_EMAIL` に追加する。
  Google Cloud Console の OAuth 同意画面が「テスト」ステータスの間は、そのアカウントを
  **OAuth 同意画面の「テストユーザー」にも追加しないとログイン自体ができない**
  （デプロイ手順.md 3-2 参照。管理者権限とは別に必要）。

### 11.0.1 `/admin` は開くたびに毎回 Google 再ログインを挟む（`lib/admin-auth.ts`）
- 通常のログインセッション（180 日スライディング、`sonae_session` Cookie）だけでは
  `/admin` に入れない。`ADMIN_EMAIL` に一致するアカウントであっても、**Google 再ログインを
  済ませてから 20 分以内**（`ADMIN_VERIFIED_MAX_AGE_MS`）でなければ、
  `app/admin/page.tsx` は常に `/api/auth/google?dest=admin` へ `redirect()` する。
- `dest=admin` の Google 認可フローはカレンダー系スコープを要求しない
  （`lib/google.ts` の `IDENTITY_SCOPES` = openid/email/profile のみ）。
  戻り先のコールバック（`app/api/auth/google/callback/route.ts`）は、通常ログインのような
  カレンダー初回同期・watch 登録は行わず、`isAdminEmail()` を満たしたときだけ
  `issueAdminVerifiedCookieValue()` で「確認した時刻」を自己署名した値を
  `sonae_admin_verified` Cookie（`path=/admin`、20 分で失効）に入れて `/admin` に戻す。
- `/admin` 側は `isAdminVerifiedCookieValid()` でこの Cookie の署名と経過時間だけを
  検証する（**消費はしない**）。当初は 1 回限りの使い切りトークンを URL の `?a=` に
  乗せる方式だったが、スマホでのスクロール中の pull-to-refresh などで意図せず
  ページが再読み込みされるたびにトークンが「二重使用」扱いになり、20 分どころか
  数秒でログイン画面に戻されてしまう不具合が発生したため、この時間帯ベースの
  Cookie 方式に変更した（旧方式の `AdminLoginToken` テーブルは
  `20260914090000_drop_admin_login_token` マイグレーションで削除済み）。
  20 分の猶予内なら、再読み込み・スクロール・別タブでの再アクセスでも
  ログイン画面には戻されない。20 分を過ぎたら、また Google 再ログインが必要になる。
  管理者以外は 10.0 通り最初の `isAdminEmail()` の時点で 404 になり、この
  再ログイン導線自体を一切見せない。
- これはセッション Cookie の偽造・使い回しだけでなく、「本人は気づかないうちにログイン済み
  セッションが残っていた」というケースへの追加の防御。`ADMIN_EMAIL` の設定ミス
  （11.0 参照）そのものは防げないので、環境変数の値は変更のたびに必ず見直すこと。
- **ブラウザに複数の Google アカウントがログイン済みの場合の罠**: `dest=admin` の
  認可 URL には `prompt=select_account consent` を使い、必ずアカウント選択画面を
  挟む（`consent` 単独だと、既にアクティブな Google セッションがあるとアカウント選択が
  省略され、意図しないアカウントのまま認証されてしまうことがある）。
  さらにコールバック側では、`isAdminEmail(profile.email)` が false のとき
  （＝選んだアカウントが管理者ではなかったとき）は **`setSession()` を呼ばない**。
  これを怠ると、管理者アカウントで既にログインしていた人が確認のつもりで別アカウントを
  選んでしまった場合に、アプリ全体のログインまでそのアカウントに書き換わってしまい
  （＝元の正しいアカウントからログアウトしたのと同じ状態になり）、
  「正しいアカウントなのに管理画面に入れない」という分かりにくい不具合になる。
  失敗時は元のセッションを変えずに `/admin` へ戻し、`isAdminEmail()` 通過済みの
  ユーザーであれば再ログイン導線に再度入れるようにする。
- **失敗理由の可視化**: 上記のいずれの失敗（state 不一致・トークン交換エラー・
  アカウント不一致）も、`/admin?err=state|exchange|mismatch&who=...` として
  `/admin` に戻し、`isAdminEmail()` を通過したユーザーには理由を画面に表示する
  （`err` が無い通常の初回アクセスは、これまで通り無言で `/api/auth/google?dest=admin`
  に飛ばすだけで、この画面は挟まない）。何も表示せず `/` や `/admin` に無限に
  戻され続けると原因の切り分けができないため、必ずこの一覧のどれかに当てはめて
  表示すること。原因不明の失敗を追加したときは、ここにも理由を追記する。
- **権限テスト用スクリプト**: `scripts/test-admin-authz.mjs`。このプロジェクトは
  Supabase を使っていないため、Google の実ログインを介さずに `lib/session.ts` と
  同じ HMAC 署名で一般ユーザー役・管理者ロール想定の Cookie を直接発行し、
  `GET /admin` の応答（404 か、`isAdminEmail()` を通過して再ログイン導線に
  乗るか）を比較する。実行前にローカル `npm run dev` を起動し、`.env` の
  `ADMIN_EMAIL` に `test-admin@example.com` を一時的に含めておく必要がある
  （本番 Vercel の環境変数は触らない）。作成したテストユーザーはスクリプト終了時に
  必ず削除される。`node scripts/test-admin-authz.mjs` で実行。

### 11.1 利用時間の計測 — `lib/activity.ts`
- `recordActivity(userId)` を `getCurrentUser()`（`lib/session.ts`）の中から呼ぶ。
  ログイン中にページを開く・Server Action を叩くたびに走るが、React `cache()` で
  1 リクエストにつき高々 1 回。
- `after()` の中で `ActivityMinute` に `upsert({ where: { userId_minuteAt }, create, update: {} })`。
  `minuteAt` は現在時刻の秒以下切り捨て（UTC）、`dayKey` は JST 暦日 `"YYYY-MM-DD"`
  （`jstDayKey`、`lib/activity.ts` からエクスポート）。**同じ分に何度呼ばれても 1 行のまま**
  （一意制約 `@@unique([userId, minuteAt])` に任せる冪等 upsert）。失敗は握りつぶす
  （集計用の副次記録であり、本編の処理を邪魔しない）。
- 「利用時間」は行数（＝アクティブだった分数）で近似する。ページ内容・操作内容は記録しない。
- cron/webhook など `getCurrentUser()` を経由しない経路（セッションを持たない）では記録されない
  ＝ここでの「利用時間」は常に「本人が実際にログイン中の画面を開いていた時間」。

### 11.2 集計クエリの組み方（`app/admin/page.tsx`）
- 利用時間の集計は素の `findMany` ではなく `groupBy` で:
  - `groupBy({ by: ["userId"], _count: { _all: true }, _max: { minuteAt: true } })` →
    ユーザーごとの累計分数＋最終アクセス日時を 1 クエリで。
  - `groupBy({ by: ["userId", "dayKey"] , _count: { _all: true } })` → (ユーザー, 日) ごとの
    分数。グループ数＝アクティブ日数、`_count._all`＝その日の分数。直近 N 日の表はここから
    JS 側でスライスする（日付ごとに別クエリは投げない）。
- はじめかたの「③ 準備リストを見た」は User に直接のリレーションが無いため、
  `Event.findMany({ where: { checklistItems: { some: {} } }, select: { userId: true },
  distinct: ["userId"] })` で「1件でも項目を持つ予定がある userId」の集合を作って判定する。
- 確定回数（メッセージを「育てた」目安）は
  `EventFutureMessage.groupBy({ by: ["userId"], where: { status: "confirmed" }, _count: { _all: true } })`。
- ユーザー数が数人規模の検証版という前提での設計。数百人規模になったら日別テーブルの
  ページングや期間指定を足すこと（現状は決め打ちで直近 `DAYS_SHOWN`=14 日）。

### 11.3 はじめかたステップの判定（管理画面版）
`app/components/getting-started.tsx` の判定条件をサーバー側だけで再現している:
`googleAccount` の有無 / `event` 件数 / 準備リストを持つか（11.2）/ `pushSubscription` 件数 /
`tutorialSeenAt`。**「ホーム画面に追加」だけは `localStorage` の自己申告のみで、
サーバーには一切保存されないため管理画面では判定できない**（帯に明記）。将来これを
知りたくなったら、`GettingStartedClient` から「追加した」を押した時点でサーバーにも

### 11.4 利用状況ランキング（ページ・機能・ⓘ・案内ポップアップ）
- **モデル**: `FeatureEvent { userId, eventKey, occurredAt }`。`ActivityMinute` と違い
  分単位の重複排除はしない**素朴なイベントログ**（呼ばれた回数＝頻度をそのまま見たいため）。
- **記録の入口は2つ**（どちらも失敗を握りつぶす。集計用の副次記録が本編を壊さないように）:
  - `lib/track.ts` の `trackEvent(userId, key)` — サーバー側で `userId` が既に分かっている場所
    （ページの description、`Server Action` の中）から呼ぶ。`after()` でレスポンスをブロックしない。
  - `app/actions.ts` の `trackFeatureUse(key)` — クライアントコンポーネントから
    `void trackFeatureUse("...")` の形で呼べる薄い Server Action（`getSessionUserId()` で
    userId が取れないときは何もしない）。`InfoHint` の押下、`Tutorial`/`GuidedSetup`/
    `PageCoach`/`FirstSeen` の表示・スキップ・完了、`ChecklistEditor` の「＋追加」など
    サーバーアクションを経由しない UI イベントに使う。
- **カタログ（`lib/track-catalog.ts`）**: `PAGE_KEYS` / `FEATURE_KEYS` / `INFOHINT_KEYS` /
  `POPUP_KEYS` に `{key, label}` を列挙して一元管理。**新しい `InfoHint`・機能・ポップアップを
  足したら、ここにも忘れず追記すること**（追記しないと管理画面のワーストランキングに
  「0回」として出てこず、存在ごと見落とされる）。`POPUP_KEYS` は 1つのポップアップにつき
  `:shown` / `:skip` / `:complete`（`FirstSeen` は `:shown`/`:ack`）に分けたキーを個別に持つ
  （まとめて1レコードにはしない＝表示に対してスキップが多い、が一目で分かるように）。
- **InfoHint の id**: `<InfoHint id="...">` の `id` は必須プロップ。`INFOHINT_KEYS` の
  key（`infohint:` を除いた部分）と一致させる。
- **`PageCoach` の shown/skip/complete の切り分け**: 元は「スキップ」ボタンも最終ステップの
  「次へ」も同じ `finish()` を呼んでいて区別できなかった。`finish(skipped: boolean)` に変え、
  スキップボタン・Escape キーは `finish(true)`、`next()` が最終ステップを超えたときと
  対象要素が見つからず打ち切ったとき（`bail()`）は `finish(false)` にした。`Tutorial` も
  同様に「スキップ」＝`finish(true)`、最終スライドの「はじめる」＝`finish(false)`。
- **カテゴリの新規作成 vs 既存選択の切り分け**（`updateEventCategory`）: `getOrCreateCategory`
  は upsert なので作成/更新のどちらでも同じ戻り値になる。呼ぶ前に
  `prisma.category.findUnique` で存在確認し、無かった場合だけ
  `feature:category-create` を記録する。
- **管理画面側の集計** (`app/admin/page.tsx`):
  - `prisma.featureEvent.groupBy({ by: ["userId", "eventKey"], _count: { _all: true } })` を
    1回だけ呼び、`Map<eventKey, Map<userId, count>>` に整形（`usageByKey`）。
  - `buildUsageRows(catalog, usageByKey, userIds)` が、カタログの全項目を
    `{ label, perUser: number[], total, avg }` に変換し、**`total` 降順**で返す
    （＝上位がランキング、`total===0` を含む下位がワーストランキング）。
  - `<UsageMatrix>` が「項目 × 利用者」の行列表＋合計列＋平均列として描画する
    （利用時間の日別表と同じ、1列目 sticky ＋横スクロールのパターン）。
    「ユーザー別」＝各利用者列、「一ユーザーあたり」＝平均列、「全体の総数」＝合計列を
    1つの表で同時に見せている（個別に3種類×2方向×4カテゴリ＝24個の表を並べるのではなく、
    ソート済みの1つの行列で代替する設計判断）。

## 12. 準備リストの項目ごとの「次回の出し方」（範囲つきルール）

項目を追加・削除したとき、その項目を次回どの予定で出す（出さない）かを指定できる。
一時期（2026-10-10）は「未来の自分へ」の scope・キーワード指定も同じ3択の形に統一していたが、
2026-10 のうちに**メッセージ側は3択を廃止**（§6.5・§12.5 参照。キーワードが決まっていること
自体が条件なので、項目のような範囲の選択は不要という判断）。キーワード入力欄
（`KeywordSentenceField`）と正規化ロジックだけは、今も両方で共有している。

### 12.1 範囲（`ItemScope`、`lib/item-scope.ts`）
画面に行で常時出る**クイック選択は次の3つ**（`QUICK_SCOPES`、`app/components/scope-picker.tsx`）。
タップするだけで即保存、詳細を開く必要は無い。3つが横に並んで折り返さないよう、
ボタンの表示文言は 2026-10-10 に短縮した（`SCOPE_CHIP`、`app/components/scope-chip.tsx`）。
以下の「意味」欄が元の長い言い回し、（）内がボタンの実際の表示文言。
| 値 | 意味（ボタンの表示） | 挙動 |
| --- | --- | --- |
| `event_only` | 今回だけ（今回だけ） | ルールを作らない。この予定の中だけ（自動学習の対象からも外す） |
| `similar` | 似た予定のとき（似た予定） | **2026-10〜**: 日時・長さ（`featureSignature`）ではなく、AIが判断した
  「同じ種類」（例: バスと新幹線はどちらも「移動」）で当てる。ルール作成時に一度だけ AI に
  「この予定と同じ種類とみなせる言い換え語」を聞き、`genre`（カテゴリ一致）と同じ
  `genres`/`genreKeywords` に保存する（`classifySimilarKind`、`lib/item-scope.ts`）。
  AI 未設定・失敗時（言い換え語が空）だけ、旧来の `featureSignature` 一致にフォールバックする |
| `keyword` | この名前の予定だけ（この名前） | タップした時点の**予定名から自動でキーワードを1つ決める**（`pickKeyword`、
  `lib/text-norm.ts`）。以後、予定名＋説明欄（自アプリのブロックを除く）にそのキーワードが
  含まれる予定で当てる |

AI が推奨するのは `event_only` / `similar` の2つだけ（`keyword` は AI は提案しない。手動選択のみ）。

詳細を開いたときだけ出す**任意のオプション**がもう1つ。クイック選択の `keyword`（予定名から自動）を、
別の語に差し替えたいときに使う。
| 入力欄 | 挙動 |
| --- | --- |
| `KeywordSentenceField`（「『＿＿』のとき」の文章欄） | 自由な語を `keywords` にセットし、`scope` を `keyword` にする |

`genre`（この系の予定のとき・ジャンル関連語やカテゴリで当てる）と `auto`（自動で覚える＝
従来の `LearnedRule` に任せる）は、**クイック選択からは外した**（2026-10-10）。
`ItemScope` 型・`ChecklistScopeRule` のデータ・`scope-match.ts` の一致判定は、既存データの
後方互換のためそのまま残している（`genre`/`auto` で保存済みの行は、引き続き効く）。
新しく `auto` になるのは、項目を一度も範囲つき操作していないとき（＝範囲行自体が無い）だけ。

### 12.2 データ（追加のみ・マイグレーション `20261004100000_checklist_scope`）
- `ChecklistScopeRule`: 範囲つきルール本体。`action`（include＝出す／exclude＝出さない）、
  `kind`（枠）、`normTitle`、`title`、`scope`、`genres` / `genreKeywords` / `keywords` / `categoryIds` /
  `signature`、`sourceEventId`、`reason`、`archivedAt`（外したルール）。`userId` 必須。
  `categoryIds` は新規作成では使わなくなった列（後方互換のため残す）。`genres`/`genreKeywords` は
  **2026-10〜、`similar` スコープが使う**（AI が判断した「同じ種類」の言い換え語。§12.1 参照。
  `genre` スコープと同じ列を流用）。`signature` は `similar` の旧データ・AI 未設定時のフォールバック用。
- `EventChecklistScope`: 予定ごとの項目の範囲。キーは `(eventId, kind, normTitle)`
  （`ChecklistItem.id` は保存のたびに作り直されるため使わない）。`status`: `proposed`（AI の提案のまま適用中）／
  `chosen`（ユーザーが選んだ）／`dropped`（打ち直しで消えた提案。AI の回数計算に残すため削除しない）。
  `source`: `ai`／`default`／`user`。`ruleId` は `ChecklistScopeRule` へ（`SetNull`）。
- 既存テーブルの列・行は変えない。既存の `LearnedRule` は消さず、並存させる。

### 12.3 提案（AI）と保存
- `saveChecklist`（`app/actions.ts`）で、追加・削除があったとき `proposeScopesForSave` を呼ぶ。
  - 残っていない「追加の提案」は `dropped` にしてルールを archive（打ち直しの後始末）。戻ってきた項目の「削除の提案」は外す。
  - 新しく現れた項目（＝まだ提案が無い）に、AI（`gpt-4o-mini`、JSON 出力）で範囲を推奨する。
    推奨できるのは `event_only` / `similar` の2択だけ（キーワードは AI は提案しない。手動のみ）。
  - **AI の上限**: 1 予定あたり `AI_JUDGE_CAP_PER_EVENT = 8` 回まで（`source='ai'` の行数で数える）。
    超えた分と OpenAI 未設定時は `event_only`（安全側のデフォルト）。タイムアウト 8 秒、リトライ無し、失敗時も `event_only`。
  - 既に `proposed` / `chosen` の行は AI を呼ばない（同じ項目で毎回呼ばない）。
  - `similar` に決まったとき（AI の推奨でも、ユーザーが直接ボタンで選んだときも）は、
    `buildRuleData` がもう一度 AI を呼ぶ（`classifySimilarKind`、タイムアウト 12 秒、
    こちらは `AI_JUDGE_CAP_PER_EVENT` の対象外）。これは「event_only か similar か」の判定とは
    別物で、「似た予定」を「どの種類とみなすか」（言い換え語）を決めるためだけの呼び出し。
- 範囲が決まった項目は、従来の自動学習（`recordEdit`）の対象から外す（`isAutoScopeDecision`）。
  `event_only` を「学習しない」にするため。範囲行が無い（＝未操作）項目は従来どおり学習する。
- `setItemKeywordScopeAction` / `setItemKeywordScope`（`lib/item-scope.ts`）: 詳細の文章欄から
  キーワードを設定する専用の経路。空文字で呼ぶと `event_only` に戻す。
- 保存処理の失敗では保存を止めない（try/catch して `console.error`）。

### 12.4 適用（一致判定）
- `buildChecklistForEvent`（`lib/suggest.ts`）の最後で、有効なルール（`archivedAt` null、`userId` で絞る）を
  `resolveScopeRules`（`lib/scope-match.ts`）で当てる。同じ項目に複数当たったら
  **キーワード ＞ ジャンル・カテゴリ（後方互換の旧データのみ）＞ 似た予定**、同じ優先度なら新しく更新されたもの。
- `applyScopeDecisions`: 除外（exclude）は組み立て済みの項目から外し、追加（include）は重複させず足す。
  範囲ルールは自動学習（`LearnedRule`）より優先する。
- 一致判定の正規化（NFKC・小文字・ひらがな化）は `lib/future-messages.ts` の既存関数を再利用
  （`includesNorm` を export）。`normTitle` は `lib/text-norm.ts`（循環 import を避けるため分離）。

### 12.5 画面
- **共通部品**（`app/components/scope-picker.tsx`）:
  - `ScopeQuickToggle` — 「今回だけ」「似た予定」「この名前」（意味は今回だけ／似た予定のとき／
    この名前の予定だけ）の3択ボタン。横に並べて一列に収まるよう文言は短くしてある。
    **行に常時表示し、タップするだけで即保存する**（詳細を開く必要が無い）。**項目専用**
    （2026-10〜。「未来の自分へ」のメッセージは3択を持たないので使わない。下記参照）。
    3番目（`keyword`）をタップしたときの実際のキーワードは、呼び出し元が `pickKeyword(予定名)`
    で決めて送る（`ScopeQuickToggle` 自体は3択のどれが押されたかを `onChange` で返すだけで、
    キーワードの算出は持たない）。`showHint`（既定 `true`）で、ボタンの右に
    `InfoHint id="scope-quick-toggle"` を出す（3択の説明）。
  - `KeywordSentenceField` — 「『＿＿』のとき」の空欄にキーワードを書く、文章形式の入力欄。
    詳細（∨）を開いたときだけ出す任意のオプション（3番目のクイック選択が自動で決めた語を、
    別の語に差し替えたいときに使う）。空にして確定すると「今回だけ」に戻る。
  - チップの見た目（色・アイコン）自体は `app/components/scope-chip.tsx` の `ScopeChip` のまま
    （3段階の色は維持。`genre`/`auto` の表示エントリも、旧データ表示用に残っている）。
  - **`InfoHint` の `open`/`onOpenChange`（制御あり）props**: 項目行（`<li key={it.key}>`）は
    自動保存が完了するたびに `it.key` が振り直されて丸ごと再マウントされる（下記 §12.5
    「予定詳細の項目行」および該当 `useEffect` のコメント参照）。`InfoHint` を内部 state
    （`useState`）のままにすると、ポップアップを開いた直後に保存が完了して再マウントされ、
    開いた瞬間に閉じてしまう不具合になる（2026-10 に発覚・修正）。`ScopeQuickToggle` は
    `hintOpen`/`onHintOpenChange` を受け取れるようにし、`ChecklistEditor` 側の
    再マウントされない階層（`openKeys` と同じ階層）に `scopeHintOpen` を 1 つだけ持たせて
    渡す（全項目で共有。説明文の内容は項目に依存しないので 1 個で足りる）。
- **予定詳細の項目行**（`checklist-editor.tsx`）: 項目名の下に `ScopeQuickToggle`（3択）を常時表示
  （即切り替え。`keyword` タップ時は `pickKeyword(event.title)` を使う。`setItemScopeAction` が
  そのままサーバー側で同じキーワードを導出するので、クライアントからキーワード文字列を
  送る必要は無い）。詳細（∨）を開くと `KeywordSentenceField` が出る（キーワード指定中は
  行にも `「…」` を小さく表示）。`setItemScopeAction`（3択）／`setItemKeywordScopeAction`
  （カスタムキーワード）いずれも、未保存の編集を先に保存してから呼ぶ（`router.refresh`）。
  `ScopeQuickToggle` 自体の `InfoHint` に加え、予定詳細ページを開いたとき
  `User.scopeHintDismissedAt` が `null` なら `ScopeHint`（`app/events/[id]/scope-hint.tsx`、
  `desc-link-hint.tsx` と同じ全画面ポップアップのパターン）を自動表示する。
  `DescLinkHint` と同時に出さないよう `showDescLinkHint` のときだけ抑制する
  （`page.tsx` の `showScopeHint = !showDescLinkHint && !user.scopeHintDismissedAt`）。
  「今後表示しない」＋OK で `dismissScopeHint()` → `scopeHintDismissedAt` を埋める。
- **未来の自分へ**（`future-message-rows.tsx` の行・`message-review-card.tsx` の確定カード・
  `/failures` の `message-list.tsx`）: **`ScopeQuickToggle` は使わない**（2026-10〜。キーワードが
  決まっていること自体が条件なので、項目のような3択は不要という判断）。`KeywordSentenceField`
  だけを出し、行の表示も🏷「＿＿」のとき／キーワード未設定の2通りのみ。保存は常に
  `scope:"keyword"`（フォームの `scope` フィールドも固定値として送る）。
  ジャンル欄・カテゴリ指定チェックボックスは既に廃止済み（`categoryOptions` の受け渡しも
  全経路で削除済み）。「メッセージを書く」（`/failures`）・予定詳細の「＋ 追加」の作成フォームも、
  本文＋キーワードだけ。`lib/message-proposal.ts` の AI 提案も `genres`/`categoryIds`/`scope`
  を出力させなくなった（SYSTEM プロンプトから削除。常に固定値で返す）。
  音声入力（`lib/dictation-to-message.ts`・`message-dictation-input.tsx`）もジャンル抽出をやめ、
  本文＋キーワードだけを AI で整える。
- **学習内容の項目**（`/savings` の「編集」を開いた中）: 予定詳細と同じ `ChecklistEditor` を使い、項目の範囲チップと選び直しも同じ。
  範囲は `lib/learning.ts` の `getLearningNameTree` が予定ごとに `eventChecklistScopes`（キーワードは
  紐づく `ChecklistScopeRule.keywords` の先頭1件を `firstRuleKeyword` で）読み、項目へ `scope` として渡す
  （渡し忘れると、選び直した直後に表示が「自動」に戻る不具合になる。2026-10 に修正）。
- **学習内容**（`/savings` の `scope-rule-list.tsx`）: 有効なルールを文章で一覧（例「「玉姫殿」を含む予定のとき：名刺を出す」）。
  「ルールを外す」は確認ポップアップのあと `archiveScopeRuleAction`（ルールを archive し、紐づく予定側の行を `auto` に戻す）。
