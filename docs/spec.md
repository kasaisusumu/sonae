# そなえ(working title) — Web App 開発仕様書 (MVP)

## 1. プロダクト概要

予定をカレンダーに入れるだけで、その予定に必要な準備リストを自動生成し、ユーザーの編集内容を学習して「自分専用マニュアル」に育てていくアプリ。過去の失敗(うっかり損失)を記録すると、類似の予定で自動的に警告を出し、再発を防ぐ。防いだ失敗の推定損失額を月次で可視化する。

ターゲット: 注意の切り替えや段取りが苦手な人(ADHD傾向)。

## 2. このMVPの目的(検証したい問い)

これはプロダクション用アプリではなく、**3〜5名のユーザーに1週間使ってもらって検証するためのプロトタイプ**。以下を確認したい。

1. 「失敗ログをつける」という行為を、ユーザーが継続できるか
2. 節約額ダッシュボードが、課金意思(WTP)を動かす実感につながるか
3. 「編集を学習して次回反映」という体験が、実際に「自分に合ってきた」と感じられるか

この目的から外れる作り込み(本番品質の認証基盤、実カレンダー連携、決済など)は今回は不要。**動くものを最速で3〜5人に触ってもらう**ことを優先する。

## 3. コア機能(優先順位順)

### 3.1 予定の登録(P0)
- **Google Calendar 連携が必須要件。** OAuth 2.0でユーザーのGoogleアカウントに接続し、Google Calendar APIで予定を取得する
  - 直近〜将来の予定を一覧取得し、そなえ側のEventとして取り込む
  - 新規予定の検知(polling、またはpush通知/Webhookが簡単に組めるならそちらでも可。MVPでは数分おきのpollingで十分)
  - 取り込んだ予定にカテゴリを付与する必要がある(Googleカレンダー側にはカテゴリ概念がないため、そなえ側で予定タイトル・説明文からカテゴリを推定し、ユーザーが確認・修正できるようにする)
- 手動でのカテゴリ修正・予定の直接登録(カレンダーに入れる前に試したい場合)も画面上でできるようにする
- カテゴリ例: 旅行・出張、通院、来客対応、契約・手続き、その他(ユーザーが自由入力できるようにする)

### 3.2 準備リストの自動生成(P0)
- 予定のカテゴリ・タイトル・日時から、準備タスクを生成する
- MVPでは、Claude APIに予定情報を渡し、準備タスク(タイトル・タイミング・チェックボックス)をJSONで返してもらう形でよい(ルールベースにこだわらない)
- 生成後、ユーザーがそのリストを編集(追加・削除・タイミング変更)できる

### 3.3 編集の学習("自分マニュアル")(P0)
- ユーザーがリストを編集した内容を、カテゴリ単位で記憶する
- 次回、同じカテゴリの予定を登録したときに、過去の編集を反映した状態でリストを生成する(例: 「ホテルは不要」と一度消したら、次回から旅行カテゴリでは出さない)
- 実装方針: カテゴリごとに「学習済みの除外項目・固定項目・タイミング調整」を保存し、生成プロンプトに含める、あるいは生成後にルールで後処理する。凝った機械学習は不要。

### 3.4 失敗ログ & 再発防止(P1)
- 「うっかり失敗」を記録する簡単なフォーム(何が起きたか、推定損失額、関連カテゴリ)
- 同カテゴリの予定を新規登録した際、過去の失敗ログがあれば警告として表示する
  - 例: 「前回、このカテゴリで『新幹線に乗り遅れ、¥25,000の損失』がありました。今回は出発1時間前のリマインドを追加しますか?」

### 3.5 節約額ダッシュボード(P1)
- 失敗ログに基づき、「防げた」とユーザーが確認した項目の推定損失額を積み上げて表示
- 月次の合計、カテゴリ別内訳、月ごとの推移グラフ
- **「推定節約額」であることを明示**し、断定的な表現(「あなたは¥18,400節約しました」等の言い切り)は避ける。「参考値」「推定ロジック: ○○」という注記を必ず添える
- ユーザーが「これは防げた」と自己申告するシンプルな仕組みでよい(自動判定は不要)

### 3.6 簡易フィードバック導線(P1)
- 各画面の隅に「このアプリに月いくらなら払いたいか」等、軽いフィードバックを収集できる導線(1問アンケート程度)を仕込む。WTP検証のため。

## 6. 推奨技術スタック

- **フレームワーク**: Next.js (App Router) + TypeScript
- **スタイリング**: Tailwind CSS
- **DB**: SQLite(ローカル検証用)+ Prisma ORM。将来的にPostgres(Supabase等)へ移行しやすい構成にする

- **認証**: MVPではGoogleログイン自体をユーザー認証として使い、そなえ独自のID/パスワード管理は不要にする(実装がシンプルになる)。複数人でのプロトタイプテストでも、各自のGoogleアカウントでログインしてもらえばよい
- **デプロイ**: Vercel(検証用に手早く公開できる)

## 9. 精度・速度の改善要件(P1完了後の修正)

Googleカレンダー連携・予定取り込みは実装済み。ここでの課題は「連携する/しない」ではなく、**同期の速さ・学習の的確さ・UIの使い勝手**。

### 9.1 カレンダー同期の即時化

現状はpollingベースでの新規予定検知のため、Googleカレンダーに予定を追加してからそなえ側に反映されるまでにラグがある。これをGoogle Calendar APIのpush notification機能で即時化する。

- **Webhook方式への切り替え**: Google Calendar API の `events.watch` を使い、カレンダーに変更があった瞬間にWebhookで通知を受け取る
  - `/api/calendar/webhook` エンドポイントを新設
  - チャンネル登録情報(`channelId`, `resourceId`, `expiration`)を `UserGoogleAccount` に保存
  - チャンネルの有効期限は最大7日のため、自動更新処理が必要(Vercel Cron Jobs等で日次チェック)
- **増分同期**: Webhook自体には変更内容(差分)が含まれないため、受信をトリガーに `events.list` を `syncToken` 付きで呼び、差分だけを取得する(毎回全件取得しない)。`syncToken` は `UserGoogleAccount` に保存し、次回以降の差分取得に使う
- **フォールバックpolling**: Webhookが届かない・チャンネルが失効した場合に備えて、軽量polling(例: 30分に1回)を保険として残す

```
UserGoogleAccount に追加するフィールド:
  - watch_channel_id, watch_resource_id, watch_expiration, sync_token
```

### 9.2 学習と提案のロジック(設計方針から書き直し)

**課題**: 現状は `CategoryLearning` がカテゴリ単位(「旅行・出張」等)でしか編集を記憶しないため、粒度が粗すぎる。同じ「旅行・出張」カテゴリでも「国内日帰り出張」と「海外1週間出張」では必要な準備がまったく異なるのに、同じ学習内容が一律で適用されてしまう。

ただし、粒度を細かくするだけでは不十分。**「学習が進むほど、リストが太って信頼できなくなる」のが一番避けたい失敗パターン。** データが増えるほど精度が上がるのは良いが、精度は「項目数を増やすこと」ではなく「出す項目・タイミングをより的確にすること」で担保する。以下、その考え方に基づく設計方針とルール。

#### 基本方針

- **目的は精度であって量ではない**: 学習データが増えても、デフォルトで項目数を増やす方向には働かせない。増えたデータは「どの項目を削るか・固定するか・いつにするか」の精度を上げるために使う
- **データが薄いときに無理に個別化しない**: 過去の類似事例がほぼない状態で「学習した風」の演出をしない。素直に一般的な準備リストを出す
- **「編集した」ことだけを強いシグナルとして扱う**: ユーザーが明示的に追加・削除・タイミング変更した操作のみを学習対象にする。「何も編集しなかった」ことを「このリストが完璧だった」という肯定シグナルとしては解釈しない(単に確認していないだけの可能性が高いため)
- **学習内容はブラックボックス化しない**: 何が学習され、なぜその項目が出ている/消えているのかを、ユーザーが確認・訂正できるようにする

#### 具体的なルール

1. **反復して確認された編集だけを「確定ルール」にする**: 同じパターンで2〜3回連続して同じ編集(例: 毎回「ホテル予約」を削除)が確認されて初めて、以後は毎回聞き直さず確定的に適用する。1回しかない編集は「仮の学習」として弱く扱い、次回も表示はするが確信度が低い状態にとどめる
2. **矛盾が起きたら確信度を下げる**: 一度削除した項目を、次の似た予定で再びユーザーが追加した場合、その項目に対する学習の確信度を下げる。決めつけて消し続けない
3. **「何を含めるか」と「いつやるか」は別のシグナルとして学習する**: 項目の有無についての学習とタイミング(前日/当日など)についての学習を混ぜて1つのスコアにしない。片方の変更がもう片方の学習を上書きしないようにする
4. **新しいカテゴリ・パターンには賢く振る舞おうとしない**: 過去データが全くないカテゴリ・パターンでは、無理に既存の学習から類推せず、素直に一般的なAI生成リストを出す
5. **古い学習内容は時間とともに重みを下げる**: 引っ越し・転職など生活状況の変化で過去の編集が古くなる可能性がある。一定期間(目安半年)更新がない学習内容は確信度を徐々に下げ、AI生成側の一般的な判断も混ぜて再提示する
6. **カテゴリをまたいだ学習の持ち込みはしない**: 「旅行・出張」の学習を「通院」のリストに影響させない。類似度マッチングはカテゴリ内に閉じる
7. **項目数に上限の目安を持たせる**: 1つの予定あたり3〜7項目程度を目安にし、学習によって項目が際限なく積み増されないようにする。上限を超えそうな場合は確信度の低い項目から削る
8. **ユーザーが学習内容を見て・直せる画面を用意する**: 設定に「学習内容の確認」ページを設け、カテゴリごとに「固定されている項目」「よく削除される項目」「確信度が低くまだ仮の状態の項目」を一覧表示し、個別に削除・固定・リセットできるようにする

#### データモデル変更案(`CategoryLearning` を置き換え/拡張)

```
EventFeature
  - id, event_id
  - is_overseas (bool, nullable)       // タイトル・場所のキーワードから推定
  - duration_nights (int, nullable)    // 予定の日付範囲から算出(日帰り=0)
  - is_weekday (bool)
  - keywords (json配列)                // タイトル・メモから抽出した主要キーワード

EditRecord  // 個々の編集をイベント単位で記録(生ログ)
  - id, event_id, category_id
  - added_items (json)
  - removed_items (json)
  - timing_changes (json)
  - created_at

LearnedRule  // EditRecordを集約した「実際に提案時に参照するルール」
  - id, category_id
  - feature_signature (json)      // どのEventFeatureパターンに紐づくか
  - rule_type ("exclude_item" | "fixed_item" | "timing_override")
  - target (string)               // 対象項目名、またはタイミングラベル
  - confidence (float, 0-1)       // 確信度。反復確認で上昇、矛盾で低下、未更新で経年劣化
  - confirmed_count (int)         // 連続で確認された回数
  - contradicted_count (int)      // 矛盾が起きた回数
  - last_confirmed_at (datetime)
  - is_user_locked (bool)         // 「学習内容の確認」画面でユーザーが固定/削除した場合
```

#### 提案生成ロジック

1. 新規予定の作成時、`EventFeature` を抽出する(ルールベースの軽い推定でよい。必要ならAnthropic APIに投げて抽出させてもよい)
2. 同カテゴリ内の類似パターンに紐づく `LearnedRule` を取得する。`confidence` が閾値(例: 0.7)以上のものは確定ルールとして強制適用(`exclude_item`→生成候補から除外、`fixed_item`→必ず含める、`timing_override`→タイミングを上書き)
3. `confidence` が閾値未満のもの(仮の学習)は、強制はせず「提案として弱めに表示し、ユーザーが1タップで却下・確定できる」形にする
4. ベースの準備リストはAI(Claude API)に一般的な内容を生成させ、その上に確定ルールを適用する。学習データが薄い場合は、この一般的な生成結果がほぼそのまま出る
5. 生成後の項目数が目安の上限(3〜7)を超える場合、`confidence` が低い項目から間引く
6. ユーザーが今回の予定でこのリストを編集したら、`EditRecord` を1件追加し、該当する `LearnedRule` の `confirmed_count`/`contradicted_count`/`confidence` を更新する

**注意**: これは既存の `CategoryLearning` テーブルを廃止して `EventFeature` + `EditRecord` + `LearnedRule` に置き換える設計変更になる。移行が必要な場合は、既存データを `confidence` 低めの初期値で `LearnedRule` に変換しておくと、データを失わずに移行できる。


### 9.3 UI改善(モバイルでの使い勝手)

そなえは主にスマホで使われる想定(予定の直前に確認する場面が多い)だが、現状はPC想定のレイアウトのまま運用されている可能性が高い。以下を優先的に見直す。

- **タップ領域の見直し**: ボタン・チェックボックス・リンクの最小タップ領域を44×44px以上に統一する。特にチェックリストのチェックボックスは指で押しやすい大きさか確認する
- **親指リーチを意識した配置**: 主要な操作(チェックを入れる、保存する、予定を追加する)を画面下部に寄せる。ナビゲーションを画面上部の小さいメニューだけに頼らない(下部固定のアクションバー等を検討)
- **フォーム入力の最適化**: 失敗ログの金額入力は数値キーパッドが出るようにする、日時入力はネイティブの日付ピッカーを使うなど、モバイルのソフトウェアキーボード・入力補助に合わせる
- **縦スクロールの短縮**: 予定登録・チェックリスト編集などのフォームが長くなりすぎないよう、セクションを分けるかステップ形式にする
- **PWAとしての表示崩れ確認**: 現状 `viewport-fit=cover` が設定されているが、ノッチ・ホームバー周りのセーフエリア(iPhone等)を考慮したpadding調整ができているか確認する
- **実機・実際の画面幅での確認**: 375px前後(iPhone SE相当)の小さい画面幅で、文字の折り返しや要素のはみ出しがないか確認する
- **保存・完了操作の即時フィードバック**: モバイル回線は不安定な場面もあるため、チェックリストの編集や失敗ログの保存時に、通信中・完了・失敗が視覚的にすぐ分かるようにする(スピナー、トースト通知等)

### 9.4 Google Calendarの説明欄への自動書き込み(任意機能)

準備リストが生成・更新されたタイミングで、該当するGoogleカレンダーの予定の説明欄に、そなえのアプリページへのリンクを自動的に書き込む。

**前提として、これはオプトイン機能にする。** 現状「カレンダーは読み取りのみ」と公開ページで明言しているため、デフォルトOFFにし、設定画面で明示的にオンにしたユーザーのみ書き込みを行う。オンにする際は、スコープ追加の再認証(Google側の同意画面)が発生する旨をユーザーに伝える。

**スコープ変更**: `calendar.readonly` → `calendar.events`(イベントの読み書き用スコープ。カレンダー全体の設定変更権限までは不要)

**書き込み内容**: まずはURLのみのシンプルな内容にする(チェックリストの中身まで転記すると、そなえ側の編集とズレて混乱の元になるため)。

```
--- そなえ ---
準備リストはこちら: https://sonae-teal.vercel.app/events/{event_id}
---
```

**既存の説明欄を壊さない**: 上記のように区切りマーカー(`--- そなえ ---` 〜 `---`)で囲み、更新時はこのブロックのみを置き換える。ユーザーが元々書いていた内容の末尾に追記する形で統一する。

**無限ループ防止**: そなえ側からGoogle Calendarへの書き込みは、9.1のWebhook(`events.watch`)によって「変更」として再検知されてしまう。これを防ぐため、書き込んだ内容のハッシュを保存し、Webhook受信時にハッシュと一致する変更であれば同期処理をスキップする。

```
Event に追加するフィールド:
  - description_write_enabled (bool, default: false)
  - last_written_hash (string, nullable)  // そなえが最後に書き込んだ内容のハッシュ。無限ループ防止用
```

**書き込みタイミング**: 準備リストの初回生成時、およびユーザーが編集を確定した後に書き込む。編集のたびに即座にAPIを呼ぶとリクエストが増えすぎるため、デバウンス(例: 編集操作が5秒止まったら書き込む)を検討する。

**ランディングページ・プライバシーポリシーの文言修正**: この機能を実装する場合、「カレンダーは読み取りのみ」の記述を「読み取りのみ(オプションで、準備リストへのリンクを説明欄に追記することも可能)」等に修正する。
