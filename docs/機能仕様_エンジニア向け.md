## 1. 技術スタック

| 項目 | 内容 |
| --- | --- |
| フレームワーク | Next.js 16.3.3 App Router / React 19 / Turbopack |
| 言語 | TypeScript |
| DB | PostgreSQL（本番 Neon / ローカルも Neon 可）、Prisma 6.19.3 |
| 認証 | Google OAuth 2.0（`googleapis`）。ログイン＝Google 連携を兼ねる |
| 通知 | Web Push（`web-push` / VAPID）＋ Service Worker (`public/sw.js`) |
| AI | OpenAI（既定 `gpt-4o-mini`、`OPENAI_MODEL` で変更可）。未設定時はルールベースにフォールバック |
| スタイル | Tailwind v4（`@import "tailwindcss"` / `@theme inline`）。白黒トークン設計 |
| デプロイ | Vercel（`prisma generate && next build`）。cron は外部から `/api/cron/poll` を叩く |

- Prisma Client の出力先は `generated/prisma`（`schema.prisma` の `generator.output`）。
  `binaryTargets = ["native", "rhel-openssl-3.0.x"]`。
- マイグレーションはローカルで実行: `./node_modules/.bin/prisma migrate deploy` → `prisma generate`。
  `datasource` は `DATABASE_URL`（pooled）と `DIRECT_URL`（直結・マイグレーション用）。

### Tailwind v4 の注意
- important 修飾子は**サフィックス**（`text-surface!`）。プレフィックス（`!text-surface`）は無効。
- 要素の既定スタイル（`a{}`, `h1,h2,h3{}`）は必ず `@layer base` に置く。unlayered だと
  `@layer utilities` に勝ってしまい `text-white` などが効かなくなる（CTA 文字消えバグの原因）。
- テーマトークンは `app/globals.css`。`--teal*` / `--accent*` は無彩色化済み。
  `--warn` / `--warn-soft` は赤（失敗警告の例外）。`--chart-amount` / `--chart-count` はグラフ専用。

## 3. データモデル（`prisma/schema.prisma`）

### 3.1 認証・ユーザー
- **User** `{ id, name?, email(unique), createdAt, tutorialSeenAt? }` — 本人識別は `email`。
  ログイン毎に upsert。`tutorialSeenAt` は導入チュートリアルの完了/スキップ時刻
  （PWA で `localStorage` が分かれても再表示しないためサーバー側にも保持）。
- **UserGoogleAccount** `{ userId(unique), googleAccountEmail, accessToken, refreshToken?,
  tokenExpiry?, calendarId="primary", lastSyncedAt?, syncToken?, watchChannelId?, watchResourceId?,
  watchExpiration?, writeDescriptionEnabled=true }` — トークン管理と watch チャンネル、
  説明欄書き込みのオプトイン（既定 true）。
- **PushSubscription** `{ userId, endpoint(unique), p256dh, auth, userAgent? }` — 1 ユーザー複数端末。

### 3.2 予定・準備リスト
- **Category** `{ userId, name, @@unique([userId,name]) }`
- **Event**（要フィールド）
  - `title, eventDatetime, endDatetime?, memo?, googleEventId?(unique), recurringEventId?`
  - `source "google"|"manual"`, `categoryId?`
  - `autoManaged`（既定 true）— 自動生成・説明欄書き込みの対象か。連携時に既にあった予定は false。
    アプリで能動的に触ると true になる（`markAutoManaged`）。
  - `listCustomized` — 個別編集して同名グループから切り離したか。
  - `listCleared` — 意図的に全消しした状態。true の間は自動生成・提案なし（「何も出さない」を学習）。
  - `sectionOrder` — 枠キーと表示順の JSON `string[]`。既定 `["task","belonging"]`。
    センチネル `"@faillog"`（`FAILURE_LOG_KEY`）が「考えられる失敗」枠の位置を持つ。
  - `listReviewedAt?` — 生成物を編集せず「確認しました」を押した日時。**編集でも `markAutoManaged`
    経由でセットされる**（＝編集＝確認済み扱い）。null かつ EditRecord 無しで「未確認」。
  - `failureWarningAckAt?` — 先回り警告を畳んだ日時（これからの予定のみ）。
  - `noFailureAt?` — 事後「なかった」を押した日時。
  - `notifiedAt?` — 新規追加通知を送った日時。
  - `lastWrittenHash?` — 最後に説明欄へ書いた内容のハッシュ（再書き込み・ループ防止）。
  - `lastInboundHash?` — 直近取り込んだ受信テキストのハッシュ（webhook と cron の二重取り込み防止）。
  - `postFailureCheckNotifiedAt?` — 事後「防げた？」通知の送信日時。
  - リマインド系: `listReminderLeads`（JSON `number[]`・分・最大5・早い順、`[]`=送らない）、
    `sentListReminderLeads`（送信済み JSON `number[]`、leads 変更で `[]` にリセット）、
    `listReminderLeadMinutes?`（先頭値ミラー・後方互換）、`listReminderTouchedAt?`（明示変更で学習停止）。
- **ChecklistItem** `{ eventId, kind, title, comment?, isDone, isUserAdded, sortOrder,
  notifyLeadMinutes?, notifiedAt?, isSuggested, suggestionType?, suggestionRuleId?, suggestionValue? }`
  - `kind` = `"task"`（準備すること）/ `"belonging"`（持ち物）/ ユーザー枠名。
  - `comment` はユーザーの自由メモ（学習対象外だが説明欄には出る）。
  - `isSuggested=true` は confidence 低めの提案行（UI では現在ほぼ非表示）。
- **ChecklistItemImage** `{ eventId, kind, slot(=正規化タイトル), data(data URL), width, height, bytes }`
  - `saveChecklist` は項目行を毎回作り直すため、画像は項目 id ではなく `(eventId, kind, slot)` で紐づく。

### 3.3 学習（spec 9.2）
- **EventFeature** `{ eventId(unique), isOverseas?, durationNights?, isWeekday, timeBucket?, keywords }`
  — 予定の軽い特徴量（ルールベース推定）。
- **EditRecord** `{ eventId, categoryId?, addedItems, removedItems, timingChanges, notifyChanges }`
  — 個々の編集の生ログ（JSON）。
- **LearnedRule** `{ categoryId, featureSignature, itemKind, ruleType, target, value?,
  confidence, confirmedCount, contradictedCount, lastConfirmedAt, isUserLocked,
  @@unique([categoryId,itemKind,ruleType,target,featureSignature]) }`
  - `ruleType` = `"exclude_item"` | `"fixed_item"` | `"timing_override"`。
  - `featureSignature` = `{d?,o?,w?,t?}` の JSON（`lib/signature.ts`）。`"{}"` は何にでも当たる。
  - `confidence` は反復確認で上昇、矛盾で低下、未更新で経年劣化。`CONFIDENCE_THRESHOLD = 0.7`。

### 3.4 失敗ログ・節約
- **FailureLog** `{ userId, categoryId?, eventId?, description, featureSignature, estimatedLossYen=0,
  outcome?, occurredAt }`
  - `outcome`: `null`=未選択 / `"linked"`=紐付け（採用） / `"prevented"`=防げた /
    `"not_prevented"`=防げなかった / `"irrelevant"`=今回は関係ない。
  - `eventId` あり＝その予定に紐づく。`eventId` なし＝カテゴリ全体（`featureSignature="{}"`）。
  - **「採用しなかった提案」= `eventId` あり かつ `outcome=null`**。結果確認の対象から除外される
    （`/failures` の各セクション、ナビのドット、事後通知の判定すべて）。
- **SavingsEntry** `{ userId, eventId?, failureLogId?, amountYen, confirmedByUser,
  @@unique([eventId,failureLogId]) }` — 1 予定 × 1 失敗ログにつき「防げた」は1回だけ。
  ダッシュボードは `confirmedByUser && failureLog.outcome==="prevented"` を集計。
- **FailureDismissal** `{ userId, eventId, descKey(=clusterKey), @@unique([eventId,descKey]) }`
  — 提案を「消す」と作られ、その予定では同じ内容を再提案しない。

### 3.5 テンプレート・その他
- **ListTemplate** `{ userId, kind, name, sourceEventId?, @@unique([userId,kind,name]) }` /
  **ListTemplateItem** `{ templateId, kind, title, notifyLeadMinutes?, sortOrder }`。
- **Feedback** `{ userId, wtpYen?, comment?, screen? }` — WTP アンケート。/admin で閲覧。

## 5. 主要コンポーネント（`app/`）

### 横断（`app/components/`）
- `landing.tsx` — 未ログインページ（`<Landing>`）。見せ所①学習リスト（`LearnMock`）／②失敗ログ→節約額（`FailMock`）。
- `prevent-goals.tsx` — ログイン直後の一番はじめのポップアップ「防ぎたい失敗はなんですか?」
  （`localStorage["mm_prevent_goals_v1"]`）。5択を複数選択 → `seedFailureGoals(labels)` が
  カテゴリ全体の `FailureLog`（`eventId:null, categoryId:null, outcome:null, estimatedLossYen:0,
  featureSignature:"{}"`、同名は重複追加しない）を作る。終了時、チュートリアル未完なら
  `mm:open-tutorial` を投げて引き継ぐ。
- `tutorial.tsx` — 概念スライド4枚のオーバーレイ（`localStorage["mm_tutorial_v3"]`、root に
  `data-mm-tutorial`）。自動表示は `mm_prevent_goals_v1` が立ってから。`mm:open-tutorial`
  イベントで再生（手動再生は常に可）。完了・スキップ時は `markTutorialSeen()` で
  `User.tutorialSeenAt` も更新する。`<Tutorial tutorialDone>`（layout がサーバー値を渡す）が
  真なら自動表示しない ＝ PWA をホーム画面に追加して `localStorage` が分かれても再表示しない。
- `first-seen.tsx` — `<FirstSeen id title>`。機能に初めて出会ったときの 1 回きり説明モーダル
  （`localStorage["mm_seen_<id>"]`）。親は機能が画面に出ているときだけマウントする
  （例: `FailureListEditor` 平常版で `rows.some(r => r.outcome === null)` のとき
  `id="failure_suggestions"`）。`[data-mm-tutorial] / [data-mm-coach] / [data-mm-guided]` が
  出ている間・概念チュートリアル未完了の間は出さず、次の機会に回す。
- `getting-started.tsx`（server）→ `guided-setup.tsx` + `getting-started-client.tsx` を同じ完了フラグで描画。
  - `GuidedSetup` — ログイン直後の1工程ずつポップアップ。未完の先頭ステップのみ表示、自動前進、
    「あとで」= `sessionStorage["mm_guided_setup_hidden_v1"]`、Tutorial 完了まで出さない。
    通知ステップは `NotifyEnableButton` でその場オン。
  - `GettingStartedClient` — 据え置きの進捗カード（同じ5手順）。
- `push-controls.tsx` — `PushControls`（設定ページ）と `NotifyEnableButton`（オンボーディング用の軽量版）。
- `notify-nag.tsx` — `<NotifyNag publicKey hasSubscription>`（layout が全ページでマウント）。
  通知がオフのままなら「通知がオフのままです」ポップアップを出し、中の `NotifyEnableButton`
  でその場オン。出す条件: **standalone（ホーム画面に追加したアイコンから起動。
  `matchMedia("(display-mode: standalone)")` or iOS `navigator.standalone`）**、
  `hasSubscription`（サーバーの `PushSubscription` 件数 > 0）が偽、
  端末側 `getSubscription()` も無し、`pushSupported()`、`localStorage["mm_tutorial_v3"]` あり、
  `sessionStorage["mm_notify_nag_v1"]` 無し、他オーバーレイ（`data-mm-*`）が出ていない。
  「あとで」= `sessionStorage["mm_notify_nag_v1"]`（その訪問のみ抑止・次回また出す）。`z-[59]`。
- `sw-register.tsx` — SW 登録＋SW からの `{type:"navigate"}` メッセージで `location.assign` するフォールバック。
- `bottom-nav.tsx` / `menu-button.tsx` / `live-sync.tsx`（ポーリング更新）。
- `page-coach.tsx` — ページ別コーチマーク。対象要素をスポットライトし、説明カードは
  **ハイライトと重ならない**よう、上下の空きが広い側に置いて空き高さに合わせて縮める
  （足りなければ内部スクロール）。背の高い対象は `scrollIntoView({block:"start"})` で
  上端を画面上部へ寄せてから測る。**導入チュートリアルが完全に終わるまで**
  （`tutorialDone` サーバー値 or `localStorage["mm_tutorial_v3"]`）はツアーを出さない。
  未完なら代わりに「先にアプリの使い方を見ませんか?」の誘導ポップアップを出す
  （「使い方を見る」= `mm:open-tutorial`／「あとで」= `sessionStorage["mm_coach_nudge_v1"]`）。
  他のオーバーレイ（`[data-mm-tutorial] / [data-mm-guided] / [data-mm-firstseen] /
  [data-mm-prevent-goals]`）が出ている間も待つ。ツアーは `TOURS`（`key` ごとに
  `localStorage["mm_coach_<key>"]` で1回きり。`key` を上げると再表示）。予定詳細の
  `event_v5` は初回に ①`[data-coach="checklist"]`（たたき台）②`[data-coach="dictation"]`
  （🎤 話して作る＝音声入力を先に使わせる）③`[data-coach="item-expand"]` ④`[data-coach="add-item"]`
  （直す＝学習、次の似た予定に反映）の順で出す。
- `savings-dashboard.tsx` / `prevented-chart.tsx` / `monthly-prevented-popup.tsx`。
- `info-hint.tsx` — 中央固定モーダルの ⓘ（`<span>`/`<button>` のみで `<p>`/`<h1>` 内でも valid）。
- `confirm-button.tsx` / `confirm-link.tsx` / `submit-button.tsx`（`confirm` prop 対応）。
- `private-mode-notice.tsx` — シークレットモード検知（`navigator.storage.estimate()` ヒューリスティック）。

### 予定詳細（`app/events/[id]/`）
- `checklist-section.tsx`（server）— `ensureChecklistForEvent`、`getWarningForEvent`、`getApplicableRules`、
  `SectionList` の組み立て（`orderedKeys` に `FAILURE_LOG_KEY` を含める）。`after()` で `refreshEventFromGoogle`。
- `checklist-editor.tsx`（client）— 1 枠ぶんの編集。**文言・メモ・追加・削除すべて自動保存**
  （`structEdited` / `commentDirty` を 1.8s デバウンス → `saveChecklist(..., includeMemo:true)`）。
  保存中は `<AutosaveIndicator show={pending}>`（`app/components/autosave-indicator.tsx`、
  黒地・白文字・右下固定。`window.visualViewport` の縮小ぶんを `bottom` に足して
  キーボードに隠れない位置へ）。見出し行右端に「全部消す」
  （`clearChecklistSection`、確認あり、学習に流さない）。「その他 ▾」= メモ一括/テンプレ/他予定コピー/名前保存。

## 6. 失敗ログ・振り返りの内部仕様（`lib/failures.ts` ＋ 関連 Server Action）

### 6.1 型と選択
- `LogRow` / `LOG_SELECT` に `outcome` を含む。
- `WarningCluster` に `thisEventLogId`（この予定に紐づくメンバーの id。決着済みを優先）を含む。

### 6.2 提案の自動材料化 — `ensureSuggestedFailures(eventId, userId)`
- `EventFailureLog` の先頭で呼ぶ。過去の予定 (`isPastEvent`) には作らない。
- `suggestFailureLogsForEvent(eventId, 6)`（ゆるいスコアリング: base 0.4、+2 同カテゴリ、+2 `eventLinkApplies`、
  +1 signature、+1.5 similarText、×decay、score ≥ 0.9 で採用）の候補を、`clusterKey` で既存重複を除いて
  `FailureLog {eventId, outcome:null}` として idempotent に作る。

### 6.3 先回り警告 — `getWarningForEvent(eventOrId)`
- カテゴリ内の `outcome != "irrelevant"` の FailureLog を集める → `logApplies`（`eventLinkApplies` かつ
  `signatureMatches`）で `strong` に絞る。
- **`isPast` のときは `strong` をさらに `l.eventId === event.id` に限定**（振り返りで出すのはその予定に
  登録された失敗だけ。カテゴリ全体・他の回は出さない）。これからの予定では従来どおりカテゴリのパターンも出す。
- `buildClusters` で似た説明をまとめ、`decayMultiplier` 込みの重みで上位のみ。
  - `loggedThisEventCount` = この予定に紐づき `outcome === "not_prevented"` のメンバー数
    （提案の未確認行・ただの紐付け行では「記録済み」表示にしない）。
  - `prevented` = この予定の確定済み `SavingsEntry` があるか。

### 6.4 `/failures` の分類（`app/failures/page.tsx`）
- `eventEnded(l) = !!l.event && (endDatetime ?? eventDatetime) <= now`。
- **「結果を記録しよう」（`<ReviewQueue>`）に出すのは `linked` + 予定過ぎ + 結果未入力だけ。**
  `reviewableLogs = logs.filter(l => !!l.event && eventEnded(l) && l.outcome !== null)`
  （決着済み行も渡してスナップショット表示を継続させる）。`ReviewQueue` 内:
  `isPending = l.outcome === "linked"`、`isSettled = !!l.outcome && l.outcome !== "linked"`
  （選択肢ボタン ↔ `RetroOutcomeSelect` の切替）。マウント時に `pendingIds = logs.filter(isPending)`。
- 「これまでの記録」は折りたたみ3つ:
  - `upcomingPredictions = logs.filter(l => !!l.event && !eventEnded(l) && l.outcome !== null)`（▸ これからの失敗予測を見る）
  - `pastReviewed = logs.filter(l => !!l.event && eventEnded(l) && l.outcome !== null && l.outcome !== "linked")`（▸ 過去の失敗予測の振り返りを見る・新しい順・`StickyReviewRows`）
  - `unlinkedLogs = logs.filter(l => !l.event)`（▸ 予定に紐づかない記録を見る・状態問わず・`StickyReviewRows`）。
    「防ぎたい失敗」の種まきや「ひとこと記録」で作るカテゴリ全体の記録はここだけに出る。
    確認コーナーには一切出さない。

### 6.5 事後通知 — `notifyPostEventFailureChecks(userId)`（cron から）
- 対象: `autoManaged && postFailureCheckNotifiedAt == null && noFailureAt == null` かつ終了済み。
- `reviewByEvent`: `outcome === null` は数えない。`adopted`（`linked` 以外の決着含む）と `pending`（`linked`）を数え、
  `reviewDone = adopted > 0 && pending === 0` なら催促しない（処理済みフラグは立てる）。
- 本文で引用する失敗は `l.eventId === e.id` のものだけ。無ければ一般的な「うっかりはありましたか？」。

### 6.6 主な Server Action（`app/actions.ts`）
- `createFailureLog` — description のみ必須。金額空→0、日付は `linkedEvent.eventDatetime` にフォールバック。
  `outcome = linkedEvent ? "linked" : null`。event 紐付けなら `markAutoManaged` ＋ `syncEventDescription`。
- `logRepeatedFailure` — `outcome=not_prevented` 指定なら「防げなかった」を記録（既存の未確認/紐付け行は昇格）。
  指定なしなら「紐付け」で追加（予定詳細の「📆 過去の失敗から追加」）。
- `markPrevented` — この予定に紐づく失敗ログ1件（無ければ複製）に `outcome=prevented` を集約し、
  `SavingsEntry` を upsert。`markAutoManaged`。
- `setFailureOutcome` — 汎用の結果切替（`RetroOutcomeSelect` / `ReviewQueue` / 学習ページ）。prevented で
  SavingsEntry 作成、それ以外で削除。`markAutoManaged`。
- `updateFailureLog` / `updateFailureAmount` — 行の内容/金額編集（自動保存）。金額は SavingsEntry も揃える。
- `deleteFailureLog` — `outcome === null` の event 紐付け行を消したら `FailureDismissal` を書く。
- `clearEventFailureLogs` — この予定の FailureLog を一括削除＋`SavingsEntry` も削除＋提案由来は `FailureDismissal`。

## 7. 準備リスト生成・学習フロー

1. **生成**: 予定詳細 or 同期時に `ensureChecklistForEvent` → `buildChecklistForEvent`
   （`recallBaseChecklist` で似た過去予定から再現、無ければ `generateBaseChecklist` で OpenAI 生成）
   → `getApplicableRules` の LearnedRule を適用（fixed/exclude/timing）。
2. **編集の保存**: `saveChecklist`（Server Action）が該当 `kind` の非提案項目を入れ替え。
   - 追加/削除/タイミング変更があれば `recordEdit`（EditRecord 作成＋LearnedRule upsert：追加→`fixed_item`
     confirm＆矛盾する `exclude_item` を contradict、削除→`exclude_item` confirm＆`fixed_item` を contradict）。
   - `markAutoManaged`（`autoManaged=true` ＋ `listReviewedAt` セット）。
   - 内容が変わった編集なら `resolveNameGroupOnEdit` で同名グループの波及/切り離しを更新。
   - `after()` で `syncEventDescription`（本人＋同名 twin）。
   - 非提案項目が 0 になったら `listCleared=true`（＋残った提案も削除）。
3. **並べ替え**: `sectionOrder`（JSON `string[]`）を ▲▼ で更新。`"@faillog"` は「考えられる失敗」枠の位置。
4. **学習の粒度**: LearnedRule は `categoryId × itemKind × ruleType × target × featureSignature`。
   confidence は反復確認で上昇・矛盾で低下・経年劣化。「精度を上げる」ためのもので、リストを増やす方向には使わない。

## 8. Google カレンダー連携フロー

1. **OAuth**: `/api/auth/google`（既定は `GOOGLE_SCOPES_WITH_WRITE`＝`calendar.events` 込み。`?write=0` で読み取りのみ）
   → `/api/auth/google/callback` で `User` upsert、`UserGoogleAccount` 保存、初回 `syncAndNotify`。
2. **差分同期**: `syncAndNotify` が `events.list` を `syncToken` で差分取得 → `Event` upsert →
   `classifyEventCategoriesBatch` でカテゴリ推定 → 新規予定を push（初回同期は送らない）→
   予算内で準備リスト先行生成。
3. **push 通知（webhook）**: `ensureWatch` で `events.watch` チャンネルを期限前に張り直す。
   `/api/google/webhook` が変更を受けて同期＋`applyInboundDescription`。
4. **保険のポーリング**: 外部 cron が `/api/cron/poll`（`x-cron-secret` 認証）を叩き、全ユーザーを差分同期、
   watch 更新、`notifyPostEventFailureChecks`、`sendDueItemNotifications` / `sendDueListReminders`。
5. **アプリ→カレンダー書き込み**: `syncEventDescription` が `writeDescriptionEnabled` かつ Google 由来かつ
   `autoManaged` の予定について、元メモ＋自ブロックを合成して書く。`lastWrittenHash` と一致ならスキップ（ループ防止）。
   「未確認」（`listReviewedAt` 無し＆EditRecord 無し＆`listCustomized` 無し）のリストは「※まだ確認されていません」
   の注記付き、または書き込み自体を保留。
6. **カレンダー→アプリ取り込み**: `applyInboundDescription` が説明欄の自ブロックをパースし ChecklistItem に反映。
   `lastInboundHash` で webhook と cron の二重取り込みを防ぐ。構造変化のみ学習＆正規化して書き戻し。

## 9. 通知（Web Push）

- **購読**: `NotifyEnableButton` / `PushControls` が `Notification.requestPermission()` →
  `reg.pushManager.subscribe({ applicationServerKey: VAPID })` → `savePushSubscription`。
- **送信**: `sendPushToUser(userId, {title, body, url?, tag?})` が全 `PushSubscription` に送信。
  404/410 は購読を削除。`payload` は JSON 文字列で `url`/`tag` を含む。
- **タグ**: `event-<id>` / `prep-<id>` / `listreminder-<id>` / `failcheck-<id>` / `series-<recurringId>`。
  すべて送信側で `url` を明示している。
- **SW（`public/sw.js` v7）**:
  - `push`: `data.json()` → `showNotification(title, { data:{ url } , tag, renotify })`。
  - `notificationclick`: `data.url || urlFromTag(tag) || "/"` を解決 →
    1) 同 URL の窓があればフォーカス
    2) 既存の同一オリジン窓があれば**新規窓を増やさず**その窓を `client.navigate(targetHref)` で移動
       （同じパスでハッシュ違いだけなら `postMessage({type:"navigate"})`、`navigate` 不可でも postMessage）
    3) 窓が無ければ `openWindow`。
  - SW を編集したら先頭コメントの `v7` を上げること（`skipWaiting` + `clients.claim` で更新）。

## 10. その他の運用ルール・落とし穴

- **編集＝確認済み**: ユーザー編集アクションは `markAutoManaged` を通し、`listReviewedAt` もセットする。
  失敗ログの各アクションからも呼ぶ。「確認しました」ボタンは“見たが何も変えていない”ケース用に残す。
- **自動保存でスクロールを飛ばさない**: `revalidateAppViews()` は `revalidatePath("/", "layout")` の
  総なめ。その画面に**route-level の `loading.tsx`（＝セグメント Suspense 境界）があると、
  自動保存の再検証でフォールバックが再表示されてスクロールがトップに戻る**。`/savings` の
  `loading.tsx` はこの理由で削除した。重い集計ページでも `loading.tsx` は置かない
  （初回遷移は前の画面を保持したまま待つ。全面スケルトンは元々出していない）。
  新しく重いページを足すときも同様に注意する。
- **自動保存の徹底**: 更新/保存ボタンは置かない。テキストはデバウンス、select は即時、
  保存中は `<AutosaveIndicator>`（右下・黒地・キーボード回避）。
  ただし「変更がないのに autosave/再生成を走らせない」こと。
- **削除は必ず確認**: `window.confirm` か `ConfirmButton`。行が消える/移動する操作も対象。
- **結果操作は離脱まで消えない**: `ReviewQueue` / `RetroOutcomeSelect` などは lazy `useState` スナップショットで
  マウント中は表示を維持。明示的な「取り消す」だけは即時反映可。
- **JST 固定**: 日時の表示・入力は日本時間（`lib/format.ts` の `parseJstDate` 等）。
- **ビルド**: `prisma generate && next build`。型チェックが OOM することがあるので、必要なら
  `NODE_OPTIONS=--max-old-space-size=6144 npm run build`。
- **Prisma のファイルシステム動的アクセス警告**（`generated/prisma/*` の 2 件）は既知・無害。
- Windows のパス表記の罠: 正しくは `カレンダーwithマニュアル`（`カレンダーwにマニュアル` は誤り）。
