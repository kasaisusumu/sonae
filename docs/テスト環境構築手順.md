# そなえ テスト環境の作り方（本番に影響しない別リンク）

本番（`https://sonae-teal.vercel.app`）とは別の URL で、同じアプリを動かすための手順。
**プロジェクトごとデータベースごと本番と分ける**ことで、テスト環境で何をしても本番の
予定・失敗ログ・学習内容には一切影響しない。

このドキュメントは「作り方の手順」です。テスト環境の恒久的な仕様は
`機能仕様_テスト環境_エンジニア向け.md`、本番との今の差分は
`機能仕様_本番との差分_エンジニア向け.md` を参照してください。

## 実際の構成（2026-09-30 時点ですでに作成済み）

- **Vercel**: 本番用の `sonae` プロジェクトとは**別のプロジェクト `sonae-test`**
  （`https://sonae-test.vercel.app`）。コードは GitHub の同じリポジトリ
  （`kasaisusumu/sonae`）の **`test` ブランチ**を追跡する（`main` を追う本番とは別ブランチ、
  git 連携済み。`test` に push すると自動で再デプロイされる）。
- **Neon**: 本番プロジェクト（`sonae`, id `snowy-night-35247032`）の中に、
  **ブランチ `test`**（id `br-bold-credit-a7vvz8fg`）を作成。作成時点の本番スキーマ・
  データを複製した状態から始まり、以後の書き込みは本番と完全に分離される。
- **環境変数**: `sonae-test` プロジェクトの Production/Preview 環境変数はすべて設定済み。
  `DATABASE_URL` / `DIRECT_URL` だけテスト用 Neon ブランチの接続文字列、
  `APP_BASE_URL` / `GOOGLE_REDIRECT_URI` だけテスト用 URL、`NOINDEX`（下記参照）は
  `true`、それ以外（Google 連携の鍵・OpenAI キー・VAPID 鍵・`SESSION_SECRET`・
  `ADMIN_EMAIL`・`CRON_SECRET`）は本番と共用。
- **Vercel Deployment Protection（SSO）は無効化済み**（既定で有効だと、Vercel に
  ログインしていない人はアクセスできず「同じように使える」にならないため）。
- **検索に出さない**（ユーザー指定）: `NOINDEX=true` を設定してあるので、
  `app/robots.ts` が `/robots.txt` を全面クロール拒否にし、`app/layout.tsx` も
  `<meta name="robots" content="noindex, nofollow">` を出す（二重の対策）。
  本番にはこの変数を設定していないので、本番は従来どおり検索に出る。

新しくマイグレーションを追加したときは、本番だけでなくこのテスト DB にも
`prisma migrate deploy` を当てること（下記「マイグレーションの当て方」）。

## 残っている手動作業

以下は API/CLI からは行えず（本人の Google アカウントでの操作が必要）、
まだ完了していない：

### Google Cloud Console にリダイレクト URI を追加

本番用の設定はそのまま残し、**追加**するだけ（本番の動作には影響しない）。

1. https://console.cloud.google.com → 対象プロジェクト →
   **API とサービス → 認証情報** → 使っている OAuth クライアントを開く
2. **承認済みのリダイレクト URI → ＋ URI を追加**:
   ```
   https://sonae-test.vercel.app/api/auth/google/callback
   ```
3. 保存（反映まで数分かかることがある）
4. **OAuth 同意画面 → テストユーザー** に、テスト環境で使うアカウントが入っているか確認
   （本番と同じ画面・同じテストユーザー一覧を共有している。追加登録は不要なことが多い）

これをやっていないと、テスト環境でログインしようとしたときに `redirect_uri_mismatch`
になる。

## マイグレーションの当て方

Neon のブランチ作成時点のスキーマは本番と同じだが、**今後 `prisma/migrations` に
新しいマイグレーションを足すたびに、本番だけでなくテスト DB にも適用**する必要がある
（自動では反映されない）。ローカルの `.env` は書き換えず、コマンドだけ一時的に
テスト用の接続文字列を指定する。

PowerShell の場合:
```powershell
$env:DATABASE_URL="<テスト用 Pooled 接続文字列>"
$env:DIRECT_URL="<テスト用 Direct 接続文字列>"
npx prisma migrate deploy
```
（テスト用の接続文字列は Neon コンソールの `sonae` プロジェクト →
Branches → `test` → Connection string から確認できる。このシェルを閉じれば
設定は消える）

新しいマイグレーションを書いたら、**本番へ適用 → テストへ適用**の2回実行する運用にする
（順番はどちらが先でも構わない）。

## コードの更新の仕方

### 本番の変更をテストにも反映したいとき

`main`（本番）に入れた変更を `test` にも反映したいときは:
```
git checkout test
git merge main
git push
```
push すると Vercel が `sonae-test` を自動で再デプロイする（`main`/本番には触れない）。

### テストで試した変更を本番に昇格させたいとき

これがテスト環境を作った一番の目的。`test` で動作確認できたら:
```
git checkout main
git merge test
git push
```
push すると Vercel が `sonae`（本番）を自動で再デプロイする。**マージするまでは
本番のユーザー・本番のデータには一切影響しない**ので、本番に利用者がいる状態でも
テスト環境側で好きなだけ仕様変更・検証を重ねてから、まとめて本番へ反映できる。

新しいマイグレーションを含む変更を昇格させる場合は、本番 DB にも
`prisma migrate deploy` を当てるのを忘れないこと（上の「マイグレーションの当て方」、
向き先の接続文字列を本番用に変える）。

## 動作確認

1. `https://sonae-test.vercel.app` を開く
2. 「Google でログイン」→ テストユーザーのアカウントでログインできれば OK
   （本番アプリでログイン済みでも、ドメインが違うので Cookie は別＝影響しない）

4. `https://sonae-test.vercel.app/robots.txt` が `Disallow: /` になっていること、
   ページのソースに `<meta name="robots" content="noindex, nofollow">` が出ていること
   （検索に出さない設定が効いているかの確認。本番側は逆にどちらも出ないのが正しい）

## 運用メモ

- **通知（Web Push）**: テスト環境でも `VAPID_*` を共用しているので、通知の許可・購読自体は
  動く。ただし GitHub Actions の定期ポーリング（`poll-calendar`）は今のところ本番 URL
  （`APP_BASE_URL` の Secrets）だけを叩く設定なので、テスト環境の新着予定通知は届かない
  （アプリを開いたときの取り込み・手動「取り込む」ボタンは通常どおり動く）。テスト環境でも
  自動通知を試したい場合は、GitHub Actions のワークフローにテスト環境向けのジョブを
  追加するか、cron-job.org でテスト環境 URL 宛のジョブを別途登録する。
- **Google カレンダーの即時 webhook**（デプロイ手順.md 手順7-B）はドメインごとの確認が
  必要なので、テスト環境では設定しない前提（5分おきの自動同期・手動取り込みで足りる）。
- **削除したくなったら**: Vercel で `sonae-test` プロジェクトを削除 → git の `test`
  ブランチも削除（`git push origin --delete test`）→ Neon の `test` ブランチを削除。
  本番には一切影響しない。

## 構築時に踏んだ不具合（記録）

新規に作った Vercel プロジェクト（`sonae-test`）へ、当時の `middleware.ts`
（Next.js 16 で非推奨。`proxy.ts` に改名され、既定ランタイムが Edge → Node.js に変更）を
そのままデプロイすると `MIDDLEWARE_INVOCATION_FAILED`
（`Cannot use import statement outside a module`）で全ページが 500 になった。
本番の `sonae` プロジェクトはこの問題が起きていなかった（作成時期が古く、旧ランタイムの
挙動のまま動いていたと見られる）。`npx @next/codemod@canary middleware-to-proxy .` で
`proxy.ts` に移行して解消し、この修正は `main`（本番）にも同じコミットで反映済み。
新しく別のテスト環境を作る場合はこの問題は再発しないはずだが、もし同じエラーが出たら
`vercel logs <デプロイURL>` でランタイムエラーを確認すること。

上の修正後も全ページ 404（静的ファイルとして配信されている状態）になった。
`vercel project add` で CLI からプロジェクトを作ると、ダッシュボードの「Import」と違って
Framework Preset が自動判定されず `Other` のままになるのが原因（Next.js のルーティングを
経由しなくなる）。CLI にこれを直すサブコマンドが無いため、Vercel の REST API を直接叩いて
`framework: "nextjs"` に修正した（`PATCH https://api.vercel.com/v9/projects/<プロジェクト名>`）。
ダッシュボードの「Import」からプロジェクトを作った場合はこの問題は起きないはず。もし
`vercel project add` で新しいプロジェクトを作って全ページ 404 になったら、
`vercel project inspect <プロジェクト名>` で Framework Preset を確認すること。
