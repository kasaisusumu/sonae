# そなえ テスト環境の作り方（本番に影響しない別リンク）

本番（`https://sonae-teal.vercel.app`）とは別の URL で、同じアプリを動かすための手順。
**データベースを本番と分ける**ことで、テスト環境で何をしても本番の予定・失敗ログ・学習内容には
一切影響しない。構成は本番と同じ Vercel + Neon + GitHub。所要 20〜30分。

## 全体像

- **コードは同じ GitHub リポジトリ**（`kasaisusumu/sonae`）の**別ブランチ**（例: `test`）を使う。
  本番は `main` ブランチのまま変わらない。
- **Neon の「ブランチ」機能**で、本番 DB の複製（テスト用 DB）を作る。今のスキーマ・データを
  コピーした状態から始まり、以後の書き込みは完全に分離される（本番には一切影響しない）。
- **Vercel の Preview デプロイ**が `test` ブランチを自動でビルドし、専用の URL
  （例 `https://sonae-teal-git-test-<アカウント名>.vercel.app`）を発行する。
  この URL だけ環境変数（DB 接続先・Google 連携の戻り先）をテスト用に上書きする。

---

## 手順1: Neon でテスト用ブランチを作る

1. https://console.neon.tech を開き、本番で使っているプロジェクト（`sonae`）を開く
2. 左メニュー **「Branches」** → **「Create branch」**
3. 名前は `test` など分かりやすいものに。親ブランチは本番の `main`（既定のまま）でOK
   → **Create branch**（今の本番スキーマ・データのコピーができる。以後は独立）
4. 作成されたブランチの **「Connection string」** パネルで、本番のときと同じように2つ控える:
   - **Pooled connection**（`-pooler` 付き）→ テスト用 `DATABASE_URL`
   - **Direct connection**（`-pooler` 無し）→ テスト用 `DIRECT_URL`
   （どちらも末尾 `?sslmode=require`。Pooled は `&pgbouncer=true` も）

---

## 手順2: git に `test` ブランチを作る

ローカルで:
```
git checkout -b test
git push -u origin test
```
以後、`test` ブランチに push するたびに Vercel が自動でテスト環境を再デプロイする
（`main` には触れないので本番は無関係）。

---

## 手順3: Vercel でテスト用デプロイを設定する

Vercel は GitHub と連携済みなので、`test` ブランチを push した時点で
**Preview デプロイ**が自動で1回走る（この時点では本番と同じ環境変数を使うので注意）。

1. https://vercel.com のプロジェクト（`sonae-teal`）→ **Deployments** タブで
   `test` ブランチのデプロイを確認 → そこに表示される URL をメモ
   （形式: `https://sonae-teal-git-test-<アカウント名>.vercel.app`。以後この URL は
   `test` ブランチに push するたびに**同じ URL のまま**中身だけ更新される）
2. **Settings → Environment Variables** を開き、以下の4つを**「Preview」だけにチェックした
   別の値**として追加する（すでにある Production/Preview 共通の行はそのまま残してよい。
   同じキーで Environment が違う行を複数持てる）。追加時に「Preview」を選ぶと
   **「Specific branches」** を選べるので、`test` だけに絞ると他の Preview（PR 等）に
   影響しない:

   | Key | Value |
   | --- | --- |
   | `DATABASE_URL` | 手順1でメモした **Pooled** 接続文字列 |
   | `DIRECT_URL` | 手順1でメモした **Direct** 接続文字列 |
   | `APP_BASE_URL` | 手順3-1でメモした `https://sonae-teal-git-test-....vercel.app` |
   | `GOOGLE_REDIRECT_URI` | 同じ URL + `/api/auth/google/callback` |

   それ以外（`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `OPENAI_API_KEY` /
   `VAPID_*` / `SESSION_SECRET` / `ADMIN_EMAIL` / `CRON_SECRET`）は本番と共用でよい
   （最初のデプロイ時に Production/Preview/Development すべてにチェックして
   登録済みのため、そのままテスト環境にも渡る）。
3. **Deployments** タブ → `test` ブランチの最新デプロイ →「⋯」→ **Redeploy**
   （環境変数を追加しただけでは既存のデプロイには反映されないため）

---

## 手順4: Google Cloud Console にリダイレクト URI を追加

本番用の設定はそのまま残し、**追加**するだけ（本番の動作には影響しない）。

1. https://console.cloud.google.com → 対象プロジェクト →
   **API とサービス → 認証情報** → 使っている OAuth クライアントを開く
2. **承認済みのリダイレクト URI → ＋ URI を追加**:
   ```
   https://sonae-teal-git-test-<アカウント名>.vercel.app/api/auth/google/callback
   ```
   （手順3-1でメモした URL に `/api/auth/google/callback` を付けたもの。完全一致でないと
   ログイン時に `redirect_uri_mismatch` になる）
3. 保存（反映まで数分かかることがある）
4. **OAuth 同意画面 → テストユーザー** に、テスト環境で使うアカウントが入っているか確認
   （本番と同じ画面・同じテストユーザー一覧を共有している。追加登録は不要なことが多い）

---

## 手順5: テスト DB にマイグレーションを適用する

Neon のブランチ作成時点のスキーマは本番と同じだが、**今後 `prisma/migrations` に
新しいマイグレーションを足すたびに、本番だけでなくテスト DB にも適用**する必要がある
（自動では反映されない）。ローカルの `.env` は書き換えず、コマンドだけ一時的に
テスト用の接続文字列を指定する。

PowerShell の場合:
```powershell
$env:DATABASE_URL="<テスト用 Pooled 接続文字列>"
$env:DIRECT_URL="<テスト用 Direct 接続文字列>"
npx prisma migrate deploy
```
（このシェルを閉じれば設定は消える。次に通常の開発に戻るときは新しいシェルを使うか、
`.env` の値で `npx prisma migrate deploy` を実行し直せばよい）

新しいマイグレーションを書いたら、**本番へ適用 → テストへ適用**の2回実行する運用にする
（順番はどちらが先でも構わない）。

---

## 手順6: 動作確認

1. `https://sonae-teal-git-test-<アカウント名>.vercel.app` を開く
2. 「Google でログイン」→ テストユーザーのアカウントでログインできれば OK
   （本番アプリでログイン済みでも、ドメインが違うので Cookie は別＝影響しない）
3. 予定を入れる・失敗ログを記録する等、好きなだけ試す → 本番（`sonae-teal.vercel.app`）を
   別タブで開いて、**そちらには一切反映されていない**ことを確認

---

## 運用メモ

- **通知（Web Push）**: テスト環境でも `VAPID_*` を共用しているので、通知の許可・購読自体は
  動く。ただし GitHub Actions の定期ポーリング（`poll-calendar`）は今のところ本番 URL
  （`APP_BASE_URL` の Secrets）だけを叩く設定なので、テスト環境の新着予定通知は届かない
  （アプリを開いたときの取り込み・手動「取り込む」ボタンは通常どおり動く）。テスト環境でも
  自動通知を試したい場合は、GitHub Actions のワークフローにテスト環境向けのジョブを
  追加するか、cron-job.org でテスト環境 URL 宛のジョブを別途登録する。
- **Google カレンダーの即時 webhook**（デプロイ手順.md 手順7-B）はドメインごとの確認が
  必要なので、テスト環境では設定しない前提（5分おきの自動同期・手動取り込みで足りる）。
- **削除したくなったら**: Vercel の `test` ブランチのデプロイを削除 → git の `test`
  ブランチも削除（`git push origin --delete test`）→ Neon の `test` ブランチを削除。
  本番には一切影響しない。
- コードは本番と同じ内容から分かれているだけなので、`main` に入れた変更を試したい範囲だけ
  `test` にマージして試す、という使い方もできる
  （`git checkout test && git merge main && git push`）。
